The ecosystem for the pi coding agent includes several prominent Agent Client Protocol (ACP) implementations. Rather than having an "official" built-in ACP server out of the box, the community relies on distinct, production-gated adapter packages optimized for specific editors, IDEs, or automated pipelines. [1, 2, 3] 
The most stable and widely used implementations of ACP for the pi harness include:
## 1. svkozak/pi-acp (The Standard Reference Adapter)

* 
* Status: Highly Stable / Reference Implementation.
* Best For: Zed editor integration and generic terminal environments.
* How it works: It acts as a clean translation proxy. It spawns a background pi --mode rpc instance and seamlessly pipes standard I/O into standard JSON-RPC 2.0 ACP events. It maps streaming output to agent_message_chunk and handles tool_call events dynamically.
* Source: Available on [GitHub (svkozak/pi-acp)](https://github.com/svkozak/pi-acp). [1, 3, 4, 5, 6] 
* 

## 2. @automatalabs/pi-acp (In-Process SDK Server)

* 
* Status: Highly Stable / Enterprise Grade.
* Best For: Headless orchestration, CI/CD, and programmatic multi-agent workflows.
* How it works: Unlike the svkozak proxy, this is an in-process server. It embeds pi natively using its published Node/Bun SDK and strictly handles the ACP Version 1 specification over NDJSON. It's excellent if you need tight process isolation without sub-process overhead.
* Source: Maintained via the [Automata Labs Package Ecosystem](https://www.npmjs.com/~automatalabsteam). [7] 
* 

## 3. pi-acp-jetbrain (IDE Native Bridge)

* 
* Status: Stable / Focused Release.
* Best For: JetBrains IDEs (IntelliJ, WebStorm, PyCharm, v2026.2+).
* How it works: This adapter bridges pi specifically to JetBrains' native ACP client panel. It provides isolated multi-session tracking (mapping fresh pi instances per chat tab) and wires IDE-specific context (like code inspection markers and lint errors) back into the agent context.
* Source: See the community thread at [earendil-works/pi/discussions/8142](https://github.com/earendil-works/pi/discussions/8142). [5, 8] 
*

The library exposes quite a lot, but not all of it is currently safe to use through an `AgentSession`.

The crucial finding is:

> `resume`, `load`, `fork`, and `newSession` work at the ACP/controller level, but calling them through `session.connection` leaves the enclosing `AgentSession` out of sync.

So the protocol support exists, but the consumer-facing abstraction is not finished yet.

## What is publicly exposed

The root package exports three increasingly low-level layers:

| Layer | Main class | Purpose |
|---|---|---|
| Stable logical conversation | `AgentSession` | What an orchestration library should normally hold |
| Live connection/controller | `AgentController` | Controls one adapter connection and its current provider thread |
| Raw ACP client | `AcpClient` | Direct ACP protocol operations |

## What genuinely works at the stable `AgentSession` level

### Prompt

This is in good shape.

- Prompts are queued.
- Prompt lifecycle notifications are emitted.
- `isBusy` and queue count are updated.
- Transcript messages and activity are recorded.
- Response boundaries and messages are preserved.
- Permissions, activity, updates, attachments, and streaming are exposed.

### Handoff

This also works as a real stable-session operation.

```ts
await session.handoff();
await session.handoff({ summary: "Already prepared context" });
```

It:

1. Optionally asks the old thread for a summary.
2. Creates a new provider thread.
3. Updates `internalSessionId`.
4. Preserves `agentSessionId` and the same JS object.
5. Updates the catalog.
6. Introduces the summary into the new thread.
7. Writes transcript handoff boundaries.
8. Emits lifecycle notifications.
9. Serializes against prompts.

Current limitations:

- Same adapter only.
- Summary-generation prompt is fixed.
- Continuation-introduction prompt is fixed.
- The introduction is a user prompt, not a system prompt.
- Only normal ACP mode is supported.

### Interrupt

Works for the queued `AgentSession` operation model:

```ts
session.interrupt();
session.interrupt({ clearQueue: true });
```

It can interrupt the active controller operation and optionally resolve/reject operations which have not started.

### Harness-specific commands

These work through the stable layer:

```ts
session.internalSessionCommands;

await session.executeInternalSessionCommand("usage");
await session.executeInternalSessionCommand("status", "verbose");
```

They go through the same prompt queue, notifications, activity handling, and transcript as normal prompts.

### Startup load/reopen

This works when expressed during creation:

```ts
await AgentSession.create({
  agentSessionId: record.agentSessionId,
  providerSession: {
    kind: "load",
    internalSessionId: record.internalSessionId,
    onFailure: "error",
  },
  // adapter, catalog, transcript, etc.
});
```

This is currently the correct way to reopen a logical session. There is no separate `restoreSession()` helper.

## What is exposed but currently unsafe

Suppose a consumer does:

```ts
await session.connection.resumeSession("provider-123");
```

The controller switches correctly, but the enclosing `AgentSession` does not know that happened. Consequently:

```ts
session.connection.currentSessionId // "provider-123"
session.internalSessionId           // potentially the previous id
session.state.internalSessionId     // potentially the previous id
```

The catalog is not updated, no logical lifecycle notification is emitted, and no transcript boundary is written.

This applies to direct calls to:

```ts
session.connection.newSession()
session.connection.loadSession(...)
session.connection.resumeSession(...)
session.connection.forkSession(...)
```

Therefore these methods “work” as ACP operations, but they do not yet work as consumer-facing stable-session operations.

This is probably the most important thing to address before tightly integrating with the agents library.

## Bridge has two different meanings

`session.bridge()` exists, but its semantics depend on the mode.

In degraded mode:

- It bridges the live PTY.
- It is the same running interactive conversation.

In normal ACP mode:

- The ACP connection has no terminal to attach to.
- The library starts a separate ephemeral native CLI process.
- It bridges that process.
- It then shuts the process down.
- The active ACP `internalSessionId` is untouched.
- The terminal interaction is not part of the `AgentSession` transcript.

So it works well as an authentication/native-TUI escape hatch, but it is not currently “open the terminal of this ACP conversation.”

## Other orchestration gaps

Several operations bypass the `AgentSession` queue:

```ts
session.setMode(...)
session.bridge(...)
session.authenticate(...)
session.setConfig(...)
session.listSessions(...)
```

This has two implications:

1. They can overlap an active prompt or handoff.
2. `session.isBusy` does not include them.

Currently `isBusy` means:

> A queued prompt or handoff is executing.

It does not mean:

> No operation whatsoever is being performed on this session.

There is also a concrete notification gap in `setMode()`: it updates the stored mode/internal ID and catalog, but does not currently emit the corresponding `state_changed` notification after updating the `AgentSession` fields.

## My assessment

For an agents/orchestration library, the usable surface today is:

```ts
create/reopen
prompt
handoff
interrupt
stop
subscribe/state
list catalog/provider sessions
read/execute harness commands
config/auth/capabilities
```

But I would not yet tell the agents library to use:

```ts
session.connection.newSession()
session.connection.loadSession()
session.connection.resumeSession()
session.connection.forkSession()
```

Those break the stable-session abstraction.

The next consumer-focused pass should define and implement first-class `AgentSession` operations for provider-thread transitions. Something approximately like:

```ts
session.loadInternalSession(...)
session.resumeInternalSession(...)
session.forkInternalSession(...)
```

Each should:

- Serialize with prompts and handoffs.
- Update `internalSessionId`.
- Persist the updated catalog record.
- Emit start/completed/failed notifications.
- Define transcript boundaries.
- Keep `agentSessionId` unchanged.
- Clearly define what happens to queued work.
- Be capability-gated.
- Preserve truthful state after partial failure.

After that, we should decide whether `session.connection` remains a documented escape hatch or becomes deliberately “advanced/unsafe,” because right now it allows consumers to violate the primary invariant of `AgentSession`.








Yes—this is intentional.

The library currently distinguishes between:

- A persistent catalog of session metadata: `SessionManager`.
- One live logical conversation: `AgentSession`.
- The consumer’s collection of live sessions: owned entirely by the consumer.

There is deliberately no library-level object like:

```ts
managedSessions.load(agentSessionId)
managedSessions.switch(agentSessionId)
managedSessions.current
```

Instead, the consumer implements that composition:

```ts
const liveSessions = new Map<string, AgentSession>();

async function loadAgentSession(
  agentSessionId: string,
): Promise<AgentSession> {
  const live = liveSessions.get(agentSessionId);
  if (live) return live;

  const record = await sessionManager.get(agentSessionId);
  if (!record) {
    throw new Error(`Unknown AgentSession: ${agentSessionId}`);
  }

  const session = await AgentSession.create({
    agentSessionId: record.agentSessionId,
    adapterId: record.adapter,
    adapter: resolveAdapter(record.adapter),
    providerSession: record.internalSessionId
      ? {
          kind: "load",
          internalSessionId: record.internalSessionId,
          onFailure: "error",
        }
      : { kind: "new" },
    mode: record.mode,
    cwd: record.cwd,
    transcriptPath: record.transcriptPath,
    sessions: sessionManager,
  });

  liveSessions.set(agentSessionId, session);
  return session;
}
```

That is a good boundary for the orchestration library because “load an AgentSession” requires consumer-owned decisions:

- How adapter IDs resolve to executable configurations.
- Whether sessions stay alive or are stopped when deselected.
- Whether several sessions may run concurrently.
- What “current session” means—or whether there is one.
- Permissions and credentials.
- Recovery policy when a provider thread no longer exists.
- How sessions relate to agents, tasks, teams, or workflows.
- Whether loading is user-driven, scheduled, or automatic.

An orchestration system with `n` agents probably should not have a global current session at all:

```ts
Map<AgentId, AgentSession>
```

or perhaps:

```ts
Map<ConversationId, AgentSession>
```

“Switching” then only means changing which object receives a UI action; it does not mutate an `AgentSession`.

What the ACP library should ensure is that consumers have enough primitives to implement this cleanly:

```ts
sessionManager.get(agentSessionId)
sessionManager.list()

AgentSession.create({
  agentSessionId,
  providerSession: { kind: "load", internalSessionId },
  ...
})
```

The main missing convenience is probably not a global manager, but a reusable reopening primitive. For example:

```ts
AgentSession.fromRecord(record, {
  resolveAdapter,
  sessions: sessionManager,
});
```

or:

```ts
openAgentSession({
  agentSessionId,
  sessions: sessionManager,
  resolveAdapter,
});
```

That could remove repetitive and error-prone reconstruction without introducing a live-session registry or imposing a concept of “current session.”

So the intended ownership remains:

```text
agents/orchestration library
├── decides how many AgentSessions exist
├── stores live AgentSession references
├── selects/routes operations
└── resolves adapter policy
       │
       ├── SessionManager: persistent routing metadata
       └── AgentSession: one stable logical conversation
```

I think that original decision is sound. We should strengthen the primitives used by that higher layer, especially safe provider-thread transitions, without making this library itself the opinionated multi-agent orchestrator.
