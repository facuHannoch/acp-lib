The many commits happened because `main` was an ancestor of `aiagent/e-0001`. Git performed a fast-forward merge:

```text
main ───────────────┐
                    └─ metering commit 1
                       metering commit 2
                       ...
                       metering commit N
```

It simply moved `main` to the branch tip, preserving every branch commit.

- `git merge --no-ff` would add one merge commit, but the individual commits would remain underneath.
- `git merge --squash` would produce one large commit.

Nothing is functionally wrong with the current history. Converting it into one commit now would require rewriting the already-merged history, which I would only do if it has not been pushed and you explicitly want that cleanup.

And yes, context is now exposed separately from cumulative usage:

```ts
const context = session.contextWindow;

if (context) {
  console.log({
    used: context.usedTokens,
    limit: context.sizeTokens,
    remaining: context.remainingTokens,
    utilization: context.utilization, // 0–1
  });
}
```

For example:

```ts
{
  usedTokens: 130_000,
  sizeTokens: 200_000,
  remainingTokens: 70_000,
  utilization: 0.65
}
```

Important limitation: `contextWindow` is based on the latest ACP `usage_update` sent by the harness. If the harness does not report `used` and `size`, it remains `null`. The OpenCode metering plugin currently gives reliable per-inference usage, but it does not independently calculate context occupancy.

These values are distinct:

```ts
session.contextWindow
// Current context occupancy for the active internal thread.

session.meteringSnapshot.totals
// Cumulative usage across the stable AgentSession.

session.meteringSnapshot.ratedCosts
// Cumulative locally calculated costs.

session.providerCost
// Latest cumulative harness-reported cost for the current internal thread.
```

After a handoff or internal-thread replacement, `contextWindow` resets to `null` until the new thread reports its context. Cumulative `AgentSession` usage and rated costs remain available across the transition.




# Two problems

Both problems are real. The first is a contained bug; the second is a missing presentation-layer capability rather than a small correction to the current reader.

## 1. Response boundaries: confirmed

The exact defect is in [response.ts](/home/ffacu/q/apps/libs/acp-lib/src/response.ts:47):

```ts
return this.entries.map((entry) => entry.text).join("");
```

The library correctly maintains separate `ResponseMessage` objects, but `PromptResult.text` destroys their boundary. The existing test even codifies the broken result in [client-response-boundaries.test.ts](/home/ffacu/q/apps/libs/acp-lib/test/client-response-boundaries.test.ts:74).

Literal `join("\n\n")` is the correct default. I agree that authored leading/trailing whitespace should not be normalized.

Two refinements are needed:

- The AgentSession error path independently uses `chunks.join("")` in [agent-session.ts](/home/ffacu/q/apps/libs/acp-lib/src/agent-session.ts:2613). Fixing only `ResponseAccumulator.text` would leave failed/cancelled responses inconsistent.
- `onChunk` is explicitly the legacy boundary-blind stream. Boundary-sensitive streaming already exists through `onResponseChunk.startsMessage`. We should either:
  - document that concatenating `onChunk` does not reproduce `PromptResult.text`; or
  - change its emitted display projection at message boundaries.

I prefer preserving `onChunk` as raw text and making `onResponseChunk` the canonical boundary-aware stream.

Empty ACP text chunks are currently discarded before accumulation, so empty messages ordinarily cannot arise. We should nevertheless specify literal joining behavior rather than silently filtering entries.

Current V1 and V2 transcripts store structured assistant messages alongside the flattened text, so many existing transcripts can reconstruct the corrected combined text. If `structured` was absent or truncated, the missing separator is unrecoverable.

## 2. Canonical presentation interleaving: confirmed

The implementation currently does exactly what the report describes:

1. Activities are queued for persistence as they occur in [agent-session.ts](/home/ffacu/q/apps/libs/acp-lib/src/agent-session.ts:2955).
2. At operation completion, all activity writes are drained.
3. One combined assistant message record is appended afterward in [agent-session.ts](/home/ffacu/q/apps/libs/acp-lib/src/agent-session.ts:2582).

Although that final record contains `structured.messages`, all messages remain nested inside one physical timeline item. Their relative position around tools is gone.

The reader then exposes physical timeline records, while `listActivityStates()` folds activities and orders them by their latest revision sequence in [transcript-reader.ts](/home/ffacu/q/apps/libs/acp-lib/src/persistence/transcript-reader.ts:252). It has no concept of original presentation position.

So:

```text
assistant A → tool → assistant B
```

cannot be reconstructed canonically today.

This is also a specification change, not merely an implementation defect. The present spec explicitly defines `timeline` as physical message/activity revisions and tells consumers to upsert them. I would retain that diagnostic timeline and add a separate presentation projection.

## Important refinement: message versus presentation block

A protocol `ResponseMessage` and a visible chat block are not necessarily identical.

For example, the same ACP `messageId` could theoretically produce:

```text
message chunks
tool activity
more chunks for the same messageId
```

The live UI displayed two text regions around the tool. Folding both regions into one presentation item would move the later text above the tool after reload.

Therefore the presentation model should use contiguous display blocks:

```ts
interface TranscriptPresentationItem {
  presentationId: string;
  presentationPosition: number;
  recordSequence: number;
  operationId?: string;
  kind: "message" | "activity" | "reasoning" | "transition";
}
```

A message item can additionally retain `providerMessageId`. Interruption by another presentable item may create another presentation block even if the provider message ID remains unchanged.

I would also call the fields `presentationPosition` and `recordSequence`, rather than the generic `position`, because they represent different clocks.

## Recommended architecture

A single presentation sequencer should observe response chunks and activities in callback order:

```text
protocol event
  → allocate/reuse presentation identity and position
  → project through transcript capture policy
  → append durable revision
  → emit committed presentation event with actual record sequence
```

The reader then:

- folds revisions by `presentationId`;
- keeps the original `presentationPosition`;
- selects the latest revision at the requested snapshot;
- sorts by presentation position;
- paginates logical items rather than records.

Provisional token chunks remain in-memory UI events. Only after persistence succeeds does the library emit a committed presentation event matching what reload will return.

The existing `timeline` and `records` views remain valuable for diagnostics and should not be replaced.

## Crash semantics need an explicit limit

“Restart during an assistant message” needs a defined expected result. Persisting every token chunk would recreate the transcript-size problem we intentionally avoided.

A reasonable contract is:

- flush a message snapshot when presentation switches to another item;
- flush again at operation completion;
- optionally batch long uninterrupted messages later;
- after a hard crash, only committed snapshots are authoritative;
- provisional text after the last snapshot may disappear.

That preserves interleaving without producing one JSONL record per token.

## WebSocket boundary

The library should provide:

- committed presentation events;
- stable presentation IDs and record sequences;
- snapshot-bound history;
- a catch-up/continuity primitive.

The actual WebSocket buffering, `catch_up_complete`, and `resync_required` messages belong to `agents-core`, because those are application transport semantics. The library supplies enough information for core to implement them without parsing JSONL or byte offsets.

## V1 migration

Synthetic presentation identities based on transcript identity plus immutable legacy offsets are reasonable. But application-specific `.order.jsonl` data should be handled by an explicit importer, not silently understood by the general transcript reader.

If the sidecar cannot be reconciled unambiguously, retaining it in the migration backup and reporting reduced ordering fidelity is the honest behavior.

## Verdict

- Response whitespace: definite bug, small isolated fix.
- Presentation ordering: definite architectural gap and worth solving in the library.
- The proposed identity/position/revision model is fundamentally right.
- Before implementing the second part, we should specify contiguous presentation blocks, committed-versus-provisional semantics, crash granularity, and the separation between library catch-up primitives and application WebSocket protocol.

Ignoring V1, the problem is simply that Transcript V2 does not persist enough information to reconstruct the order visible to the user.

Today, this happens:

```text
Live ACP events:

1. assistant message A
2. tool announced
3. tool completed
4. assistant message B
```

But V2 writes roughly:

```text
seq 10: tool announced
seq 11: tool completed
seq 12: assistant response {
  messages: [A, B]
}
```

The transcript knows:

- A comes before B.
- The tool was written before the final response record.
- The tool revisions belong to one activity.

It does not know whether the original order was:

```text
A → tool → B
```

or:

```text
tool → A → B
```

That information is permanently lost. No reader algorithm can recover it from the current records.

Three pieces are missing:

1. Each assistant message must be its own durable presentation item, rather than being nested inside one final operation response.
2. Every presentation item needs a position allocated when it first appears live.
3. Revisions must retain that original position while their physical transcript sequence advances.

Conceptually:

```ts
interface PresentationMetadata {
  presentationId: string;
  presentationPosition: number;
}
```

The existing transcript envelope already provides the commit/record sequence:

```ts
record.seq
```

So we probably do not need to persist another `recordSequence` field. The reader can expose `recordSequence: record.seq`.

For example:

```text
message A:
  presentationId = "message:operation-1:0"
  presentationPosition = 20
  seq = 45

tool announced:
  presentationId = "activity:tool-7"
  presentationPosition = 21
  seq = 46

tool completed:
  presentationId = "activity:tool-7"
  presentationPosition = 21  // unchanged
  seq = 49                   // newer revision

message B:
  presentationId = "message:operation-1:1"
  presentationPosition = 22
  seq = 50
```

The presentation reader folds by `presentationId`, keeps the newest revision, and sorts by `presentationPosition`. It therefore returns:

```text
A → completed tool → B
```

The raw `timeline` reader can continue returning physical records and individual revisions for diagnostics.

There is also a live-event gap. Currently:

- response chunks have `messageId` and `startsMessage`;
- activities have an `activityId` and revision;
- transcript records have `seq`;

but no single event tells the consumer:

> “This exact logical item was committed at presentation position 21 with transcript sequence 49.”

That committed event is what would let `agents-core` delete its `.order.jsonl` sidecar.

A reasonable write strategy avoids persisting every token:

- Allocate message identity and position on its first chunk.
- Accumulate chunks in memory.
- Flush a message revision before another presentable item is committed.
- Flush again when another message begins or the operation ends.
- Activity revisions reuse their first position.
- Emit the committed event only after the transcript append succeeds.

Separately, the immediate `primitives.The` problem is only this:

```ts
messages.map(message => message.text).join("\n\n")
```

plus fixing the AgentSession error path, which independently uses `chunks.join("")`.

So the work divides cleanly:

1. Fix combined-response whitespace.
2. Add presentation identity and position to V2.
3. Persist assistant messages individually/revisionally.
4. Add a folded presentation reader.
5. Emit the same committed presentation objects live.

V1 does not need to complicate this. Its old records can remain available through the existing legacy/timeline reader and eventually be deprecated. The new authoritative presentation API can require records carrying the new V2 presentation metadata.
