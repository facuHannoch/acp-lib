# AcpLauncher and PreparedLaunch

The immediate ACP connection failure is primarily an `agents-core` bug, not an `acp-client` transport bug.

`acp-client` receives this command:

```text
docker exec -i -u devuser <container> claude-agent-acp
```

and spawns it with:

```ts
env: { ...process.env, ...(this.opts.env ?? {}) }
```

That is reasonable library behavior: `env` belongs to the process being directly spawned—which is the host-side `docker`/`podman` CLI.

But `agents-core` passes the container environment there, including:

```text
HOME=/home/devuser
```

Consequently, rootless Podman running on the host tries to store its own state under `/home/devuser/.local/share/containers`, causing:

```text
mkdir /home/devuser: permission denied
```

The relevant boundary is:

- [session.ts](/home/ffacu/q/apps/libs/agents/.agents/.workspaces/sec-hardening-f/agents-core/src/agent/chat/session.ts:63) builds the agent/container environment and passes it as `AgentSessionConfig.env`.
- [client.ts](/home/ffacu/q/apps/libs/agents/.agents/.workspaces/sec-hardening-f/agents-core/node_modules/@qlairoslabs/acp-client/src/client.ts:207) constructs the prefixed command.
- [acp-transport.ts](/home/ffacu/q/apps/libs/agents/.agents/.workspaces/sec-hardening-f/agents-core/node_modules/@qlairoslabs/acp-client/src/transport/acp-transport.ts:80) correctly applies that environment to the directly spawned process.

So the correct immediate fix belongs in `agents-core`: launch Docker/Podman with the host environment and inject the agent environment inside the container. The attach implementation already does exactly this safely in [prepare.ts](/home/ffacu/q/apps/libs/agents/.agents/.workspaces/sec-hardening-f/agents-core/src/attacher/prepare.ts:12): it preserves host `HOME`, writes the target environment inside the container, and sources it before launching the actual command.

I would not fix `acp-client` with:

```ts
env: isDockerExec ? process.env : this.config.env
```

That would make Podman connect, but silently discard secrets, harness variables, MCP-related variables, and other intended agent context.

There is, however, a worthwhile ACP-library improvement:

- Rename or clarify `env` as `spawnEnv`: environment of the directly spawned launcher.
- Let the caller provide the complete launch command/wrapper needed to establish the target environment.
- Avoid having the ACP library infer container semantics from `command[0] === "docker"` where possible.

There is also a more important adjacent problem: ACP client-side terminal requests currently use `Bun.spawn()` directly on the host in `TerminalRegistry`. With a Docker agent, an ACP `terminal/create` request can therefore execute in the hub host namespace rather than the container. Filesystem callbacks appear to have the same namespace concern. That is a real isolation boundary issue.

Until runtime-aware ACP terminal/filesystem handlers exist, `agents-core` should disable those client capabilities for Docker sessions, or the ACP library should allow the caller to supply runtime-specific implementations.

In short:

- Current Podman crash: fix in `agents-core`.
- Clearer `spawnEnv` API: useful ACP-library cleanup.
- Runtime-aware terminal/filesystem backends: ACP-library API work plus `agents-core` implementations.
- Do not put Docker-specific environment injection inside the generic ACP transport.

## Pagination

Yes, pagination should be part of the public transcript API from the beginning. We do not need to split the physical JSONL file yet.

A single append-only JSONL file is still a good storage format because:

- Appends are simple.
- Partial final writes can be detected.
- The transcript remains portable.
- Consumers can inspect it without library tooling.
- Appending new content does not move existing byte offsets.

The problem is not primarily that the file has 100,000 lines. The problem is APIs that parse all 100,000 lines to return the latest 50.

## What currently exists

The current reader already has an initial form of pagination in [transcript.ts](/home/ffacu/q/apps/libs/acp-lib/src/transcript.ts):

```ts
readTranscriptLines(path, {
  before: timestamp,
  limit: 50,
  types: ["msg", "activity"],
});
```

It reads backward from the end in chunks, which is good. But timestamps are not strong cursors:

- Multiple lines may have the same timestamp.
- They do not identify an exact byte boundary.
- Filtering makes page boundaries less obvious.
- They cannot detect replacement, truncation, or compaction.
- They become awkward once physical activity updates fold into logical records.

We should replace or complement `before: number` with an opaque cursor.

## Public API

Something like:

```ts
interface TranscriptPageOptions {
  cursor?: string;
  limit?: number;
  direction?: "older" | "newer";
  view?: "messages" | "timeline" | "raw";
  types?: TranscriptLineType[];
}

interface TranscriptPage<T> {
  items: readonly T[];

  /** Continue in the requested direction. */
  nextCursor: string | null;

  /** Useful when navigating in both directions. */
  previousCursor: string | null;

  /** Whether another page is known to exist. */
  hasMore: boolean;
}

const page = await readTranscriptPage(path, {
  limit: 50,
  direction: "older",
  view: "timeline",
});

const older = await readTranscriptPage(path, {
  cursor: page.nextCursor!,
  limit: 50,
  direction: "older",
  view: "timeline",
});
```

For the usual chat UI:

- First call returns the newest 50 items.
- Items are returned oldest-to-newest for immediate rendering.
- `nextCursor` loads the next 50 older items.
- New lines appended during pagination do not disturb the older cursor.

## Cursor internals

The cursor should be opaque to consumers but internally contain approximately:

```ts
interface TranscriptCursorPayload {
  version: 1;
  transcriptId: string;
  generation: string;

  /** Exact physical boundary in the JSONL file. */
  byteOffset: number;

  /** Logical ordering validation. */
  seq: number;

  /** Prevent using a timeline cursor with a different query/view. */
  queryFingerprint: string;

  /** Detect a changed boundary or replaced file. */
  boundaryDigest: string;
}
```

Encoded as base64url:

```text
eyJ2ZXJzaW9uIjoxLCJ0cmFuc2NyaXB0SWQiOi...
```

The consumer must not depend on its contents.

A byte offset is preferable to:

- line number, which requires counting from the beginning;
- timestamp, which is not unique;
- sequence alone, which still requires searching for its physical position.

`seq` remains useful for validation and logical ordering.

## Stable snapshot while reading

At the start of each read, capture the current complete-file boundary:

```text
snapshotEnd = last complete newline at or before current file size
```

The page reads only through that boundary. If another prompt appends while the page is being read, those new records do not unexpectedly enter the middle of the result.

A partial trailing line is ignored until it becomes complete or is repaired during writer startup.

## Cursor invalidation

Cursors remain valid while the file is append-only.

They become stale if the transcript is:

- replaced;
- truncated;
- compacted;
- rewritten during migration;
- manually edited before the cursor boundary.

The reader should throw a typed error:

```ts
TranscriptCursorInvalidError
```

It should never silently restart from the newest page, because that produces duplicates and missing entries in consumer timelines.

The `transcriptId`, generation, sequence, and boundary digest provide this detection.

## What constitutes one paginated item?

This is the most important design choice. We need separate physical and logical views.

### Raw view

```ts
view: "raw"
```

Returns physical JSONL records:

```text
header
checkpoint
message
activity update
transition
raw ACP event
```

Pagination counts physical lines. This is mainly for diagnostics and recovery tooling.

### Messages view

```ts
view: "messages"
```

Returns only logical user/assistant messages. Checkpoints, lifecycle records, and activity do not count toward `limit`.

```ts
interface TranscriptMessage {
  operationId: string;
  role: "user" | "assistant";
  text: string;
  timestamp: number;
}
```

### Timeline view

```ts
view: "timeline"
```

Returns end-user-visible logical records:

```text
message
settled tool activity
handoff/switch boundary
permission decision
usage/context event
failure/cancellation
```

Current activity records can have multiple physical updates sharing a `recordId`. Timeline pagination must fold those updates before counting them.

That means `limit: 50` means 50 logical timeline items, not “read 50 physical lines and return however many survive.”

The backward scanner may cross more than 50 physical lines to produce those 50 logical records.

## Safe folding boundaries

We should use `operationId` and turn boundaries when folding.

If the scanner encounters an activity record near a page boundary, it must continue far enough backward to determine whether earlier physical records belong to the same logical activity. It should not return two partial representations of one tool call on adjacent pages.

A practical rule:

- Scan until at least `limit` logical items are available.
- Continue to the preceding operation boundary.
- Fold all physical records within the scanned region.
- Return the requested number of logical items.
- Put the cursor before the earliest fully resolved logical item.

This may make physical scan sizes variable, but keeps consumer results coherent.

## Filtering and cursors

A cursor should belong to one query shape:

```ts
{
  view: "timeline",
  types: ["message", "tool", "transition"]
}
```

Changing the view or filter while reusing its cursor should fail validation. Otherwise a cursor created while skipping tool records could behave unexpectedly when tools are later enabled.

That is the purpose of `queryFingerprint`.

## Limits

Recommended defaults:

```ts
default limit: 50
maximum limit: 500
```

Consumers needing exports should use an explicit streaming iterator instead of requesting one enormous page:

```ts
for await (const item of iterateTranscript(path, {
  view: "raw",
})) {
  await exportItem(item);
}
```

This keeps memory bounded even for complete exports.

## Should we split the file?

Not initially.

Splitting introduces:

- segment naming and ordering;
- atomic rollover;
- cursor movement across files;
- checkpoint duplication;
- deletion and retention rules;
- portability complications;
- more recovery cases.

A single file with byte-offset pagination remains efficient for ordinary backward reads, even with hundreds of thousands of lines.

We should nevertheless keep the cursor opaque so storage can later become:

```text
transcripts/<agentSessionId>/
  manifest.json
  000001.jsonl
  000002.jsonl
  000003.jsonl
```

without changing the consumer API. A future cursor can internally contain a segment ID plus byte offset.

Segmentation becomes worthwhile based on measured file size or retention requirements, not merely line count.

## Registry pagination

The session registry should also expose a paginated API:

```ts
await sessionManager.list({
  limit: 50,
  cursor,
  order: "updated_desc",
});
```

The initial full-JSON implementation may load the registry internally, but consumers should not receive the complete catalog by default. A custom database-backed `SessionStore` can implement the same cursor contract efficiently.

So the recommended design is:

- Keep one transcript JSONL per `AgentSession`.
- Add opaque cursor pagination.
- Use byte offsets internally.
- Separate raw, message, and folded-timeline views.
- Return items chronologically within each page.
- Make cursors query-specific and detect stale files.
- Keep the API independent from future file segmentation.
- Add the same paginated shape to session listing.
