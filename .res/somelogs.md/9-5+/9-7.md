# AcpLauncher and PreparedLaunch

The immediate ACP connection failure is primarily an `agents-core` bug, not an `acp-client` transport bug.

`acp-client` receives this command:

```text
docker exec -i -u devuser <container> claude-agent-acp
```

and spawns it with:

```ts
env: { ...process.env, ...(this.opts.env ?? {}) }
```

That is reasonable library behavior: `env` belongs to the process being directly spawned—which is the host-side `docker`/`podman` CLI.

But `agents-core` passes the container environment there, including:

```text
HOME=/home/devuser
```

Consequently, rootless Podman running on the host tries to store its own state under `/home/devuser/.local/share/containers`, causing:

```text
mkdir /home/devuser: permission denied
```

The relevant boundary is:

- [session.ts](/home/ffacu/q/apps/libs/agents/.agents/.workspaces/sec-hardening-f/agents-core/src/agent/chat/session.ts:63) builds the agent/container environment and passes it as `AgentSessionConfig.env`.
- [client.ts](/home/ffacu/q/apps/libs/agents/.agents/.workspaces/sec-hardening-f/agents-core/node_modules/@qlairoslabs/acp-client/src/client.ts:207) constructs the prefixed command.
- [acp-transport.ts](/home/ffacu/q/apps/libs/agents/.agents/.workspaces/sec-hardening-f/agents-core/node_modules/@qlairoslabs/acp-client/src/transport/acp-transport.ts:80) correctly applies that environment to the directly spawned process.

So the correct immediate fix belongs in `agents-core`: launch Docker/Podman with the host environment and inject the agent environment inside the container. The attach implementation already does exactly this safely in [prepare.ts](/home/ffacu/q/apps/libs/agents/.agents/.workspaces/sec-hardening-f/agents-core/src/attacher/prepare.ts:12): it preserves host `HOME`, writes the target environment inside the container, and sources it before launching the actual command.

I would not fix `acp-client` with:

```ts
env: isDockerExec ? process.env : this.config.env
```

That would make Podman connect, but silently discard secrets, harness variables, MCP-related variables, and other intended agent context.

There is, however, a worthwhile ACP-library improvement:

- Rename or clarify `env` as `spawnEnv`: environment of the directly spawned launcher.
- Let the caller provide the complete launch command/wrapper needed to establish the target environment.
- Avoid having the ACP library infer container semantics from `command[0] === "docker"` where possible.

There is also a more important adjacent problem: ACP client-side terminal requests currently use `Bun.spawn()` directly on the host in `TerminalRegistry`. With a Docker agent, an ACP `terminal/create` request can therefore execute in the hub host namespace rather than the container. Filesystem callbacks appear to have the same namespace concern. That is a real isolation boundary issue.

Until runtime-aware ACP terminal/filesystem handlers exist, `agents-core` should disable those client capabilities for Docker sessions, or the ACP library should allow the caller to supply runtime-specific implementations.

In short:

- Current Podman crash: fix in `agents-core`.
- Clearer `spawnEnv` API: useful ACP-library cleanup.
- Runtime-aware terminal/filesystem backends: ACP-library API work plus `agents-core` implementations.
- Do not put Docker-specific environment injection inside the generic ACP transport.

- The attach path is the appropriate model: preserve a host-safe launcher environment, materialize target env inside the container, then source and `exec` it. See [prepare.ts](/home/ffacu/q/apps/libs/agents/.agents/.workspaces/sec-hardening-f/agents-core/src/attacher/prepare.ts:58).

A generic ACP transport should not special-case Docker. The proposed `isDockerExec ? process.env : config.env` would both infer runtime from argv and lose intended target context. `agents-core` can already build a wrapper with the current `execPrefix` mechanism; the library’s API/docs simply make the boundary unclear.

The isolation concern is real and more severe than a path mismatch:

- [TerminalRegistry](/home/ffacu/q/apps/libs/acp-lib/src/terminals.ts:113) calls `Bun.spawn()` locally. For a Docker ACP agent, `terminal/create` therefore executes arbitrary requested commands on the hub host.
- It also merges `config.env` into that host process at [terminals.ts](/home/ffacu/q/apps/libs/acp-lib/src/terminals.ts:116), so container-target secrets/context can be exposed to host-side terminal commands.
- [fs-access.ts](/home/ffacu/q/apps/libs/acp-lib/src/fs-access.ts:23) directly reads/writes host paths. A container agent can request host paths such as `/etc/...`; no runtime or workspace boundary is enforced.

The immediate safe core-side response is to disable `terminal` and both filesystem client capabilities for Docker sessions until runtime-backed handlers are supplied. Merely disabling terminal leaves host filesystem callbacks exposed.

ACP-library follow-up I’d recommend:

- Rename `env` to `spawnEnv` (or add it while deprecating `env`) for the launcher process.
- Add explicit pluggable terminal and filesystem handlers/backends; core can provide container implementations.
- Replace `command[0] === "docker"` with an explicit launch/cwd policy supplied by the caller. It currently happens to work for `docker`-named Podman compatibility wrappers, but not an explicit `podman exec`.

There is no transport/container integration test in this checkout covering environment separation or runtime capability isolation.
