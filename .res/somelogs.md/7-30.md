## The three read paths

**Live.** Frames arrive, `foldFrame(map, frame)` — a record replaces, a delta appends. One tool chip that fills in: title at 8, command at 13, output at 14.

**Reconnect mid-turn.** Subscribe → `session.activitySnapshot()` → `{active: true, seq: 11, records: [think-1, t1]}` → `foldRecords` those → then stream, discarding `seq <= 11`. The thinking block arrives whole, so the orphan-`append` problem doesn't exist. Reconnect *between* turns gets `{active: false, records: []}` — nothing to place, because the transcript already owns it.

**Cold reload.** `readTranscriptLines(path, {before, limit})` → `foldRecords` → last-wins on `recordId`. ## The mechanism: filter at the read layer, not after it

One option, and `limit` counts what survives it:

```ts
export interface ReadTranscriptOptions {
  before?: number;
  limit?: number;
  /**
   * Only these line types. `limit` counts what SURVIVES this filter, so
   * `{types:["msg"], limit:20}` is twenty messages, not twenty lines of which
   * some happen to be messages.
   */
  types?: Array<TranscriptLine["t"]>;
}
```

The whole implementation is one more rejection in the existing per-line parse:

```ts
function parseTranscriptLine(raw, before, types?: Set<string>): TranscriptLine | null {
  …
  if (types && !types.has(line.t)) return null;   // ← the entire change
  …
}
```

Both read paths already funnel through that function and already count only what it accepts, so the tail read starts counting messages **for free** — it walks backwards until it has `limit` survivors instead of `limit` lines. No new loop, no second pass.

Then the three public readers each declare what they're counting:

|                       | passes                | `limit` now means                            |
| --------------------- | --------------------- | -------------------------------------------- |
| `readTranscript`      | `types: ["msg"]`      | N messages ✅ fixes the bug                  |
| `readActivityRecords` | `types: ["activity"]` | N activity lines — same latent bug, same fix |
| `readTranscriptLines` | whatever you pass     | unchanged by default                         |

`readTranscript` forces `["msg"]` rather than merging a caller's `types`, since its whole job is the message projection — accepting `types: ["activity"]` there would be incoherent.

## Why this over `count: "lines" | "messages"`

`count` leaves the default wrong and makes every caller opt into correct behaviour. `types` fixes the default *and* solves the case agents-core actually has: its chat-history route wants `msg` + `activity` interleaved on one timeline, and `types: ["msg","activity"]` makes `limit` mean "50 things I'll render" instead of "50 lines, some of which are `meta` and `raw` noise I'll throw away."

## The one real cost, which I'd document rather than fix

The tail read's promise becomes weaker. Today: *cost ∝ what you asked for*. After: *cost ∝ the file region containing `limit` matches*. Ask for 20 messages in a transcript whose last 200 KB is one enormous tool call, and it scans that 200 KB. Correct, but no longer bounded by `limit` alone.

I'd state that in the docstring and stop there. A `maxScanBytes` cap is the obvious next lever, but it makes "I asked for 20 and got 6" possible again — trading a clear cost for an unclear result, which is the wrong trade for a debugging-adjacent read path.

Linear bytes, not quadratic: 400 chunks of a 4 KB block cross as ~4 KB total instead of ~800 KB.

Two things that come free: the REPL already renders thinking markers (on by default, `--no-activity` off), and with `transcriptActivity` on, each block lands as **one** settled line — 8 chunks → 1 line, not 8.

The caveat worth knowing is agent-dependent, not API-dependent: **Codex streams thinking, `claude-code-acp` sent none at all** in either run today. So a consumer should treat thinking as optional and not build UI that looks broken without it.







# !!!!!!!!!!



Here's what I'd put in front of anyone building on this library — ordered by what bites first.

## What changed for you right now

- **Delete the `chatStore` seed-on-orphan workaround** and flip its test. An orphan delta after a snapshot is a real bug signal again; keeping the workaround hides it.
- **Keep the hub's busy-set guard.** `active` is honest now (starts `false`), but it only knows what the aggregator was told — your hub knows whether a process is up. Trust yourself over it.
- **`delta ?? current` is safe by hand now.** It wasn't. `wireFrames` is still the better call, because it also carries block closes that ride in `emitted`.
- **`session.setConfig()` exists** — that's the only route to Codex's `reasoning_effort`, `model`, `mode` once a session is running.

## The rules that don't change

1. **Send `wireFrames(result)`; fold with `foldFrame`. Don't reach past them.** Three invariants live in there: closes ride in `emitted`, a base always precedes its deltas, and a record and a delta for the same `recordId` never go out together (`foldFrame` has no seq guard — it would double-append).
2. **Mid-turn joins need the snapshot first**, then discard `seq <= snapshot.seq`. `seq` never restarts, so the threshold is valid forever.
3. **One aggregator per stream, for the life of the stream.** `startTurn()` between turns, never a fresh instance — minted ids and the `seq` clock both depend on it.
4. **Absent field means *unchanged*, not empty**, and `content` replaces rather than accumulates. The fold already handles this; you only need it if you touch raw `onActivity`.

## Things that look like library bugs and aren't

- **Thinking is optional per run and per agent.** Render it when it arrives; look complete when it doesn't. And it's configured in three different *places*: environment (Claude's `MAX_THINKING_TOKENS`), ACP config option (Codex's `reasoning_effort`), nothing at all (Kimi). There is no cross-agent switch.
- **Agents are weird in ways the fold absorbs.** Claude announces each call twice; Kimi resends the entire growing tool input on every update (161 for one call); some agents send `messageId` for thinking blocks and some don't. Your renderer shouldn't care — but your *expectations about line counts* should.
- **A silent turn is usually the agent.** Kimi accepted a prompt, went quiet for 243 s, then answered `session/cancel` in 11 ms. The protocol layer was fine throughout.
- **When an agent refuses to start, the reason is on stderr and nowhere else.** `claude-code-acp` answers `session/new` with a bare `-32603 Internal error` and explains itself only in its stderr. Keep a stderr tail even when you're not wire-logging.
- **`--wire` first, always.** Every non-obvious thing we found today came from it, including proof that a suspicious concatenation was the agent's and not ours.

## The two-line version

> Take `onRecord` → `wireFrames` → `foldFrame` and render `AggregatedRecord`s. Treat thinking as optional, treat per-agent tuning as per-agent, and reach for the wire log before suspecting the library.
