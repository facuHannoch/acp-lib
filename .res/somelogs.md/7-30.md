## One turn, event by event

The 14 activity events Kimi actually sent for *"run ls and tell me the first three files"*:

| #    | wire                        | `ActivityEvent`       | aggregator              | → file                              | → socket             |
| ---- | --------------------------- | --------------------- | ----------------------- | ----------------------------------- | -------------------- |
| 1    | `available_commands_update` | `commands`            | snapshot                | — *(filtered)*                      | record               |
| 2-7  | `agent_thought_chunk` ×6    | `thinking` ×6         | accumulates             | —                                   | **6 deltas** (~40 B) |
| 8    | `tool_call`                 | `tool` pending        | closes block, announces | `think-1:settled`<br>`t1:announced` | 2 records            |
| 9-12 | `tool_call_update` ×4       | `tool_update` content | folds, nothing settles  | —                                   | 4 records            |
| 13   | `tool_call_update`          | `+rawInput`, `+title` | first input             | `t1:input`                          | record               |
| 14   | `tool_call_update`          | `status: completed`   | settles                 | `t1:settled`                        | record               |
| —    | prompt resolves             | —                     | `flush()`               | *(nothing open)*                    | —                    |

**14 events → 4 activity lines**, plus the two `t:"msg"` lines. Under the code as it stands today it'd be 14 near-duplicate lines; before this week's fix, events 9-14 arrived as `{toolCallId, status}` and the command and output were simply gone — the `{}` in your original screenshot.

Note event 8: the thinking close is emitted *before* the tool announcement, so `ts` order matches causal order. And the socket gets deltas for 2-7 (~40 bytes) rather than six growing snapshots.

## The three read paths

**Live.** Frames arrive, `foldFrame(map, frame)` — a record replaces, a delta appends. One tool chip that fills in: title at 8, command at 13, output at 14.

**Reconnect mid-turn.** Subscribe → `session.activitySnapshot()` → `{active: true, seq: 11, records: [think-1, t1]}` → `foldRecords` those → then stream, discarding `seq <= 11`. The thinking block arrives whole, so the orphan-`append` problem doesn't exist. Reconnect *between* turns gets `{active: false, records: []}` — nothing to place, because the transcript already owns it.

**Cold reload.** `readTranscriptLines(path, {before, limit})` → `foldRecords` → last-wins on `recordId`. Turn 5's `t5:think-1` and turn 5's `t1` (well, `0:tool_...`) both survive alongside turn 4's, because minted ids are prefixed and protocol ids are session-unique. Grouping is by the `msg(user) → activity… → msg(assistant)` fences; a turn missing its trailing assistant message died in flight, and its `t1:announced` line tells you what it was doing.

Same fold function in all three. That's the property the whole design is for.

## What's actually running today

**Built and tested (103 green):** everything from the wire up to `ActivityAggregator`, including terminals, the fs handlers, the interceptor, the full mapping, and the fold with its snapshot/seq/prefix semantics.

**Not built:** the `agent-session.ts` row — `startTurn`, `onRecord`, `activitySnapshot`, the `transcriptActivity` config object, and writing settled lines. So `transcriptActivity: true` still writes the raw delta dump today; the aggregator exists but nothing in the library calls it yet. Then step 3 (bounded tail read) and step 4 (contract docs).

Two things that bypass this pipeline entirely, worth knowing: **permission requests** go through the SDK as blocking requests, not through the aggregator — and updates can arrive slightly *ahead* of them, never behind, so a chip always exists before its permission prompt. And **assistant text** streams through `onChunk`, untouched by any of this; only the final string is persisted, in the assistant `msg` line.
