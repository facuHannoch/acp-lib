## 1. `ActivityAggregator` — the shared fold

New module `src/activity.ts`. Pure, no I/O, exported from the barrel. Folds the delta stream into full-state records using rules the protocol already dictates.

```ts
/** Why a record was emitted. Persisted, so readers can filter without folding. */
export type EmitReason =
  | "announced"  // tool call first seen
  | "input"      // tool call first learned its rawInput
  | "settled"    // terminal status reached, or a thinking block ended
  | "flushed"    // turn ended with the record still open
  | "snapshot";  // inherently complete on arrival (plan, usage, mode, unknown)

export interface AggregatedActivity {
  event: ActivityEvent;   // always FULL state, never a delta
  reason: EmitReason;
}

export interface ActivityAggregatorOptions {
  /** Extra checkpoint when a tool call first learns its input. Default true. */
  checkpointOnInput?: boolean;
}

export class ActivityAggregator {
  constructor(options?: ActivityAggregatorOptions);

  /** Fold one live event. Returns records in append order — often empty. */
  apply(event: ActivityEvent): AggregatedActivity[];

  /** Flush open state (thinking block, unsettled calls, coalesced usage). */
  flush(): AggregatedActivity[];

  /** Current folded view, for live rendering. */
  tool(toolCallId: string): ToolActivity | undefined;
  tools(): ToolActivity[];

  reset(): void;
}
```

One instance per turn. `AgentSession` makes one for the transcript; agents-core makes one in its socket path. **Two instances, one implementation** — that's the anti-drift property.

### Fold rules

| Input                                                    | Effect                                                                        | Emits                                               |
| -------------------------------------------------------- | ----------------------------------------------------------------------------- | --------------------------------------------------- |
| `tool`                                                   | create/replace entry                                                          | `announced`                                         |
| `tool_update` (no entry yet)                             | create from the update, defaults `status:"in_progress"`, `toolKind:"other"`   | `announced`                                         |
| `tool_update`                                            | merge: spread, `content`/`locations` replace wholesale                        | nothing, unless…                                    |
| …first `rawInput`                                        | —                                                                             | `input` (if enabled)                                |
| …status `completed`/`failed`                             | —                                                                             | `settled`, once per id                              |
| `thinking`                                               | append to open block                                                          | nothing                                             |
| any non-thinking event                                   | close open block                                                              | `settled` **before** the triggering event's records |
| `plan`, `mode`, `unknown`, `plan_update`, `plan_removed` | pass through                                                                  | `snapshot`                                          |
| `usage`                                                  | keep latest                                                                   | nothing (coalesced to flush)                        |
| `user_message`, `commands`, `config`, `session_info`     | pass through                                                                  | `snapshot`                                          |
| `flush()`                                                | close block, emit unsettled calls **with their real status**, emit last usage | `settled` / `flushed` / `snapshot`                  |

Three things worth calling out:

- **The aggregator emits everything.** It owns *semantics*, not policy. Which kinds get persisted is the writer's filter. That keeps one decision in one place.
- **Ordering is guaranteed by `apply()` returning an array** — a pending thinking block is flushed before the record that ended it, so `ts` order matches causal order.
- **`flushed` ≠ `settled`.** A turn that's cancelled or dies mid-call writes the call at its true status (`pending`/`in_progress`). That's your R4 signal, and it's honest rather than a fake terminal state.

## 3. Bounded reads

`readTranscriptLines(path, {before, limit})` keeps its signature. ## The refinement that makes both work from one API

```ts
export interface ApplyResult {
  /** Full current state of whatever this event touched. For live rendering. */
  current: AggregatedRecord | null;
  /** Checkpoints worth persisting. Usually empty. */
  emitted: AggregatedRecord[];
}

export interface AggregatedRecord {
  /** Stable identity for last-wins folding. */
  recordId: string;        // tool → toolCallId · thinking → "think-1" · plan → "plan" · usage → "usage"
```

## 1. §4.1 sends `current` on every event — that's O(n²) bytes on thinking

This is the one I'd fix before writing code, because it lands directly on the scenario that motivated the whole feature.

> the hub sends `current` on every event (full state, never a delta, so live granularity is preserved)

For tool calls that's free — the agent already resends `content` cumulatively, so `current` ≈ what we broadcast today. But **thinking arrives as incremental chunks**. A 4,000-character reasoning block in ~400 chunks currently costs ~4 KB on the wire. Sending full state each time costs ~800 KB. Two orders of magnitude, on the mobile connection this feature exists to survive.

It's also internally inconsistent: `chunk` (assistant text) stays incremental, so text streams efficiently while thinking streams quadratically.

Options as I see them: have `ApplyResult` carry the delta alongside `current` for accumulating kinds, or accept that the webapp folds thinking and revisit the packaging question in §4.2. I'd rather not have the webapp fold, because the thinking boundary is precisely the invented rule you isolated — so my preference is the first.

## 2. The round-trip test doesn't do what §3.2 says readers do

> Run a fresh aggregator **B** over the persisted lines.

Persisted lines are `AggregatedRecord`s, but `apply()` takes `ActivityEvent`s, and for thinking those are **not interchangeable**. Two persisted blocks (`think-0`, `think-1`) fed through `apply()` both append to the open block and merge into one. B would produce a different result than A, and the test would either fail confusingly or paper over it.

§3.2 says the reader's fold is `map.set(rec.recordId, rec)` — which is a different operation from `apply()`. So either the test should use `map.set` for B, or the aggregator needs an explicit `ingest(record)` distinct from `apply(event)`.

Worth being precise in the prose too: it's one implementation of the **live** fold; the persisted fold is trivially last-wins. That's still the anti-drift property you want, but "run the same aggregator over both" isn't accurate.

## 3. `recordId` for thinking is instance-local — collision risk between the two instances

`think-<n>`, n = block index within the turn. There are now **two** aggregator instances over the same stream: `AgentSession`'s (transcript) and the hub's (socket).

They agree only if both are created at turn start. The hub's socket is per-agent and long-lived — a client connecting **mid-turn** gets an aggregator starting at `n=0` while the lib's is at `n=2`. Now the same thinking block has id `think-0` live and `think-2` persisted, and after reload the webapp's `map.set(recordId)` shows it twice.

Since reconnect-mid-turn is a first-class case here, I'd derive thinking ids from something stream-derived rather than an instance counter — or at minimum state the invariant that both instances must be constructed at turn start and reset together.

```
[1]      commands             → 0 lines  (not in default kinds)
[2]-[7]  thinking ×6          → 1 line   (one settled block)
[8]      tool     announced   → 1 line
[9]-[12] tool_update ×4       → 0 lines  (folded, nothing settled yet)
[13]     tool_update rawInput → 1 line   (input checkpoint)
[14]     tool_update completed→ 1 line   (settled)
                                ────────
                                4 activity lines, was 14
```

Plus the two `t:"msg"` lines, so 6 total for the turn.

One asymmetry worth being explicit about: a **hard** crash (SIGKILL, no error path) loses an open thinking block entirely, because nothing is written until it closes — whereas a tool call's `announced` line is already on disk. That's deliberate: "what command was it running" is the debugging question, a half-finished thought isn't. If you'd want thinking checkpointed too, it's a config knob, but it puts back a chunk of the volume this design removes.

And to keep the two channels distinct: on the **socket** the hub still sees every event — `current` for tool calls, an incremental `delta` for thinking. The 2–3 line figure is only what lands in the file.

## `recordId` is turn-scoped; the transcript is conversation-scoped

A fresh `ActivityAggregator` per turn means `counters` restarts, and several ids are constants:

```ts
case "plan":  return "plan";
case "mode":  return "mode";
// usage → put("usage", …)
default:      return `${event.kind}-${this.nextCount(event.kind)}`;  // think-1, think-2, …
```

So **every turn produces `think-1`, `plan`, `usage`**. But the transcript file accumulates across turns — that's the whole point of the hub capturing `agentSessionId` so the same `<id>.jsonl` grows.

The file contract says:

> Fold last-wins on `recordId` — `foldRecords()`, live and persisted alike.

That's only true *within a turn*. Run `foldRecords()` over a 5-turn conversation and you get **one** thinking record and **one** plan — the last turn's. Turns 1–4 come back stripped of their reasoning and their plans. The tool calls survive only because `toolCallId` is harness-generated and globally unique, which is what disguises the problem.

It also can't be caught by the current suite: the round-trip test folds a single turn, where ids are unique by construction. It'd need a two-turn fixture to fail.

Cheapest fix I can see is a caller-supplied prefix — `new ActivityAggregator({ idPrefix })` with `AgentSession` passing a per-turn value, so ids become `t7:think-1`, `t7:plan`. Live and persisted still agree because they come from the same instance. The alternative — readers folding per `msg`-delimited segment — puts the work back on readers and contradicts "trivially last-wins", so I'd avoid it.
