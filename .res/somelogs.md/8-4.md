## 1. The bug — confirmed, and your patch needs two more lines

`src/client.ts:675` is exactly as you describe. Two things to correct before it lands:

**Don't fall back to `options[0]`.** Your snippet leaves `allowed` possibly `undefined`. The tempting `?? request.options[0]` reintroduces the bug for any agent that offers neither allow kind. The correct fallback is `cancelled` — if we can't identify an allow option, we don't guess, because guessing is what got us here.

**The `allow_once` → `allow_always` order is load-bearing, not stylistic.** `allow_always` writes a durable rule into the agent's own settings that outlives the session. An auto-approver silently making permanent policy decisions on the user's behalf is a different bug wearing the same shirt. Worth a comment so nobody "simplifies" it to a single `.find(o => o.kind.startsWith("allow"))` later.

Two related things while we're in there:

- **`defaultPermission: "cancel"` returns protocol `cancelled`, which is not "no".** In ACP, `cancelled` means the turn is being torn down; `reject_once` means "denied this one, carry on." Agents are entitled to treat those differently, and some abort the turn on `cancelled`. The symmetric fix is to select `reject_once` when offered. That's a behavior change, so I'd flag it rather than smuggle it in.
- **`PermissionRequest.options[].kind` is typed `string`** (`src/types.ts:175`). It's about to become the dispatch key — it should be the real union.

**Why this shipped: there is not one test in `test/` that touches permissions.** `grep -rn ermission test/` returns nothing. The fix should come with a table over option orderings — reject-first, allow-first, allow_always-only, neither — because "Claude happens to order it this way" is the kind of fact that changes under us.

## 2. The bigger flow — one premise to correct first

It isn't one-way today. `PromptHandlers.onPermissionRequest` (`src/types.ts:205`) is a blocking callback that returns `PermissionOutcome | Promise<PermissionOutcome>`, and the agent genuinely blocks on it. agents-core simply isn't passing it, so everything falls through to `defaultPermission`.

So the gap isn't "we can't ask the consumer." It's that **the shape we offer is unusable from where agents-core actually lives** — behind a process/network boundary, where the answer comes from a human clicking a button in a browser. A per-prompt in-process closure returning a promise is the wrong ergonomic for that, and the fact that nobody used it is the evidence.

Five concrete gaps, in the order they'd bite:

**No correlation id.** `PermissionRequest` carries `toolCallId`, which isn't unique (an agent can ask twice about one call) and in ACP v2 is optional entirely — a `command` subject may carry no tool call at all (`.res/v2_migration.md:496`). Nothing to key a websocket round-trip on. We should mint a `requestId`.

**No out-of-band answer path.** Today the consumer must stash the resolver in a closure and keep it alive across the boundary itself. The lib should hold the pending registry and expose `session.resolvePermission(requestId, outcome)`. Then the flow is just: event out, user clicks, RPC in — which is the shape agents-core already speaks.

**Permission requests are invisible to the fold and the transcript.** `TranscriptPermissionLine` is a declared type that *nothing writes* — the reader parses it at `src/transcript.ts:344`, no writer emits it. The aggregator never sees permission requests at all. Consequences: a client connecting mid-turn sees a spinner with no explanation for the stall, and after the fact the transcript has no record that permission was asked or what was chosen. This is the same class of bug as the thinking one we just fixed — state the consumer needs, structurally unable to reach it. It should be an `ActivityEvent` → an `AggregatedRecord` → present in `ActivitySnapshot`, settling when answered.

**No timeout, and cancel doesn't sweep.** `interrupt()` (`src/client.ts:567`) sends `session/cancel` and does nothing about an unresolved permission promise. If a human never clicks, the turn cannot end — the agent is still waiting on us. v2 explicitly requires responding `cancelled` to all pending requests on cancel (`.res/v2_migration.md:310`). We do neither.

**Policy is one global boolean.** `approve | cancel` for everything, forever. What MCP actually wants is a policy function — `(request) => outcome | "ask"` — so reads auto-approve and writes escalate. `defaultPermission` then becomes the degenerate case of that, which is a nice property: the existing config keeps working.

## 3. Commands

Related but not the same problem. `agentCommands` is exposed as data at all three layers (client/controller/session), but the only invoke path is the REPL's `//name` string convention at `src/repl/repl.ts:70` — a programmatic consumer has to know to strip a slash and send it as a prompt. `session.runCommand(name, args)` is thin, but it makes the contract explicit and gives one place to absorb the fact that some agents answer a command through `session/update` and some through the prompt result.

What commands genuinely share with permissions is only this: **the consumer needs a request/response channel out of the lib, not just an event firehose.** I'd build that channel once for permissions and let commands use it, rather than treat them as one feature.

## My recommendation on sequencing

Ship the option-kind fix alone as **0.3.2** — it's ~15 lines plus tests, it unblocks MCP today, and it doesn't need any of the design settled. Then do the request/response channel as **0.4.0**, since it adds real surface (`requestId`, `resolvePermission`, a permission record kind, policy) and deserves to be a version people opt into.

The thing I'd want your read on before designing 0.4.0: does agents-core want to **answer** permission requests (human in the loop, browser round-trip), or mostly to **observe** them while a policy auto-decides? Those pull the design in different directions — the first makes the pending registry and timeouts central, the second makes the policy function central and the registry an edge case. Your MCP problem sounds like the second, but the webapp having a permission prompt sounds like the first.
