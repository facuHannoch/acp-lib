## Diagnosis

The streaming plumbing (transport → `handleUpdate` → `onChunk`/`onActivity`) is fine. The loss happens in the **mapping layer**, `src/updates.ts`, and in the **shape of `ActivityEvent`** itself.

### 1. `tool_call_update` throws away everything except `status` — the main bug

`src/updates.ts:34-39`:

```ts
case "tool_call_update":
  return { kind: "tool_update", toolCallId: u.toolCallId, status: u.status ?? "in_progress" };
```

Per the SDK schema (`ToolCallUpdate`, types.gen.d.ts:5240), that notification carries `content`, `rawInput`, `rawOutput`, `title`, `kind`, `locations` — and in ACP the initial `tool_call` is normally emitted early with `status:"pending"` and thin/empty input; **the command, the output, and the diff all arrive later via `tool_call_update`**. The library forwards only a status string, so the consumer can never learn what the tool did. That is exactly a tool block that renders a title and `{}` and then never fills in.

### 2. There's no field to put it in anyway

`ActivityEvent`'s `tool` variant (`src/types.ts:45-56`) has `title`, `toolKind`, `status`, `rawInput` — no `content`, no `rawOutput`, no `locations`. Even the initial `tool_call` case (`updates.ts:25-33`) drops `u.content` and `u.locations`. So the output contract has no channel for tool output at all, in either event.

### 3. Whole update kinds are silently dropped

`default: return null` (updates.ts:42) swallows kinds the SDK defines: `plan_update`, `plan_removed`, `user_message_chunk`, `current_mode_update`, `usage_update`, `session_info_update`. Only the full `plan` snapshot is handled — an agent that emits `plan` once and then `plan_update`s will look frozen at the first plan.

### 4. `terminal: true` is advertised but not implemented

`CLIENT_CAPABILITIES` (`src/capabilities.ts:60-63`) claims `terminal: true`, but `ClientHandler` (`src/transport/acp-transport.ts:166-193`) implements only `sessionUpdate`, `requestPermission`, `readTextFile`, `writeTextFile`. The SDK dispatches `terminal/create` as `client.createTerminal?.(params)` (dist/acp.js:515-517) — with no method that resolves to `undefined`, so the agent gets a null result where it expects `{ terminalId }`. Because we advertised the capability, agents will choose the terminal path for shell tools, and the resulting `ToolCallContent` is `{type:"terminal", terminalId}` — which point 1 discards regardless. Given your screenshot is a *Terminal* block specifically, this is very likely compounding the problem.

Same class of issue: `fs.readTextFile/writeTextFile: true` is advertised, but `AcpClient` never passes `onReadTextFile`/`onWriteTextFile` to the transport, so reads return `{content: ""}` and writes are silently accepted-and-dropped.

### 5. No escape hatch for the consumer

`onUpdate` for raw notifications exists only on `SwitchSessionOptions` (load/resume/fork replay, `client.ts:552-557`). During a live prompt there's no raw passthrough, so your app can't work around 1-3 on its own.

### 6. Activity never reaches the transcript

`TranscriptActivityLine` is defined (`src/transcript.ts:27-33`) but nothing writes it — `AgentSession.runPrompt` only appends `user`/`assistant` msg lines. So even the activity you do get vanishes on reload.
