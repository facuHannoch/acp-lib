## Findings and notes

- **No defects found in the library or the runtime.**
- **The migration fixture is honest on the harness side and synthetic on the data side.** It does not fake the library's row: the event, the blocked row, `timezoneMigration` and the idempotent reopen come from the real runtime's open-time migration. What is synthetic is the starting state (a zone that exists in no bundle and a made-up version `0000a`, written directly into a harness-internal table, `reminder_rows`). It therefore proves the `invalid_schedule` hold path only: not `cause: "proof_budget"`, not a successful revalidation (no event), not repair by an explicit schedule update, not a genuinely older IANA release. It also couples the test to the harness's table and JSON layout.
- **Stdio filter is not proven by the production tests.** Dropping `routine` from the filter regex survives all nine tests, because with the approved runtime's client the same frames reach the host through the harness client route. The tests prove one delivery per frame on the real stdio path; they cannot distinguish which of the two routes delivered. The filter remains covered by the unit tests.
- A routine terminal mark from `reminder_expired` (my earlier D2) and a content dedupe both survive, as expected: the real harness emits neither event kind for routines, and emits no identical disposition frames.
- The `no-guard` test builds its retained intent with a second `ReminderService` that bypasses `routineUnavailable`. That is the only realistic way to hold a pre-existing routine intent against a guard-less open, but it means the offline authoring gate is exercised only by the unit tests.

## 4. storage_failure and exhaustion: is the in-process coverage adequate?

Yes for the library logic, with one residual. The approved runtime has no fault seam for the 250 ms proof budget, so the library behaviour is exercised against the scripted routine peer and is mutation-proven: the exact frozen startup batch replayed for three attempts and then `reminder_batch_retry_exhausted`; the create-then-fail marker (including the fix that a marker never blocks a later create and a non-exhausted frozen batch survives a lost session); live retry keeping the same reminder id and change id; `discardExhausted` scope, state and high-water; and non-retryable `invalid_config` handling. The runtime does emit the literal wire code `storage_failure` (`index.ts` returns it for storage errors, `testing.ts` maps open failures to it), so the code string the library matches is the one the real server produces. The residual is that the exact error shape of a real startup open failure carrying `storage_failure` has not been observed end to end; the scripted peer builds the same `HarnessClientError` class. That is a small risk, to be revisited if the runtime ever gains a seam.
