# Review — release documentation (`release-docs`: alpha `510e2a7`..`da4e0c0`)

Reviewed as documentation against the code: `CONSUMER_GUIDE.md`, `MIGRATION-0.12-to-0.13.md`, `package.json` `files` and the release-docs report. I worked from clean archives of `da4e0c0` and of alpha `510e2a7` (`/tmp/clad2a-rd`, `/tmp/clad2a-alpha2`) and from the installed 0.12.1 in agents-core's `node_modules`. I changed no tracked file and did not touch the agents-core checkout (I used scratch copies under `/tmp`). Nothing under `src/` or `test/` differs between `510e2a7` and `da4e0c0`.

**Verdict: the migration note is accurate and nearly complete, the new guide examples compile and run, and the packaging change is correct. Two things should be fixed before release (a stale README that ships in the package, and a gap in the agents-core instructions that the type-check cannot see). Then four smaller doc gaps.**

## Findings, ranked

1. **IMPORTANT: the agents-core "byte-identical baseline" proves types only; the documented edits break agents-core's runtime tests until its test doubles are updated, and the note doesn't say which.** The note's last step says "Update session test doubles used by that branch to supply `harnessConnection()`". I applied the documented source edits to a scratch copy and ran agents-core's own tests against alpha (the baseline on 0.12.1 first):

   | Test file | 0.12.1 baseline | alpha + the documented edits, doubles untouched | alpha + edits + `harnessConnection()` added to the doubles |
   | --- | --- | --- | --- |
   | `__tests__/integration/steer-delivery.test.ts` | 9 pass | **1 pass, 8 fail** | 9 pass |
   | `__tests__/integration/user-chat-acceptance.test.ts` | 11 pass | **9 pass, 2 fail** | 11 pass |

   The doubles are `connection: { currentClient: { isConnected: true } }` objects typed loosely, so the type-check can't see the gap (it restores the 112-error baseline exactly, below). They live in `__tests__/integration/steer-delivery.test.ts:35`, `__tests__/integration/user-chat-acceptance.test.ts:36`, `__tests__/kit/harness.ts:17` and `__tests__/unit/hub.test.ts` (lines 624, 660 and 752; that file can't run in a scratch tree because of a macro import, so I could not run it). The fix that worked is one member on each double: `harnessConnection() { return this.connection; }`. Name the files and give that line in the note.

2. **IMPORTANT: `README.md` still documents the removed `defaultPermission`, and it ships in the package.** The Quick start (`README.md:85–91`) builds `new AgentController({ …, defaultPermission: "cancel" })`, which no longer compiles (`TS2353: 'defaultPermission' does not exist in type 'AgentControllerConfig'`, verified), and lines 127–129 describe `defaultPermission` (`"approve"`/`"cancel"`) as the fallback. The guide, the migration note and the CLI (`--approve` now maps to `permissions: { default: "allow" }`) are right; the README, which is the first thing on the package page, is not. Update both places to `permissions: { default }`.

3. **MEDIUM: `PersistenceCapabilities.channels` is a required member, which the note doesn't say.** In 0.12.1 the interface had no `channels`; in alpha it is `channels: boolean` (required), while `workers` and `workerDelivery` are optional. A custom persistence backend written against 0.12.1 will fail to type-check until it sets `capabilities.channels` (false is fine). The note says the repositories are optional and to "advertise capabilities only when the corresponding repository is present", which reads as "omit it". Say that `channels` must be declared.

4. **MEDIUM: the checklist mixes breaking changes with new-feature behaviour.** The native rows (stop, close, suspension and resume; metering evidence; worker delivery) describe features that **did not exist in 0.12.1** (`HarnessUnavailableError`, `NativeHarnessHost`, the orchestrator and their persistence are all new exports), so they cannot break a 0.12.1 consumer. Split the table into "what breaks when you upgrade" and "new behaviour you get if you opt in". It would also help to state what I verified: **no export was removed** (0.12.1 exports 828 names; alpha has 913 and all 828 are still there), the `package.json` `exports` map and `dependencies` are unchanged, and `AgentController` is now a deprecated alias (`const` plus `type`) of `HarnessController`.

5. **MEDIUM: small type-level breaks that are not listed.** (a) `MeteringProvenance["source"]` gains `"native_ledger"`, so an exhaustive switch over it stops compiling. (b) `AgentAdapterRegistration.adapter`, `AgentConfig.adapters` and `AgentAdapterRegistry.register` widen from `Adapter` to `AgentAdapter` (`Adapter | NativeAdapter`), so code that reads `registration.adapter.command` needs a narrow (`list()` still returns the `Adapter` shape). (c) `PromptHandle` gains a required `withdrawAsync`, which affects test doubles of the handle. (d) The exported `AgentEvent` union is widened with `WorkerEvent`; `AgentEventNotification`'s default stays the record event, so `subscribe` listeners are unaffected. None of these appeared in agents-core's diagnostics, but a note that says "exhaustive switches" should name (a).

6. **LOW (packaging, user's pending decision): what the package ships.** `bun pm pack --dry-run` on `da4e0c0`: **515 files, 4.61 MB**, version still `0.12.1`, and the only difference from alpha's pack is the two new documents. Nothing sensitive: no key-like strings in any packed file (OpenRouter, `sk-`, JWT, bearer, private-key and cloud-key patterns), no `.env`, `.mcp.json` (it is at the repository root and not in `files`), auth files, logs or databases. But it ships the whole embedded harness folder: `src/native-harness/.res/` (about 1 MB of internal design docs, a marketing draft and a sandbox with transcripts), `src/native-harness/test/` (708 KB of tests and fixtures), `AGENTS.md`, a nested `bun.lock`, and **12 of those files contain the author's absolute home path** (`/home/ffacu/…/haurness-l/…`). Whether to exclude those is the pending decision; I list them so it is made knowingly. Also the guide's link to `smoke-tests/orchestrator/README.md` points outside the package (the sentence does say "from the source checkout").

7. **LOW (guide gaps).** The orchestrator section never lists the worker event kinds (`worker_opened`, `worker_busy`, `worker_idle`, `worker_replied`, `worker_reloaded`, `worker_dropped`, `worker_redirected`, `worker_failed`, `worker_stopped`) or the delivery states (`pending`, `delivered`, `blocked_policy`, `failed_destination`), although it tells the reader to subscribe and to read `deliveryState`. The section also lacks the "experimental" label that the native section keeps in its heading (it depends on the native harness and has had one live smoke run).

## What I verified (each against the code)

**1. The migration note.**

- **`defaultPermission` mapping.** `approve → allow` selects exactly what 0.12.1 did (`allow_once`, else `allow_always`, else cancel). `cancel → ask` differs as the note says: 0.12.1 returned a `cancelled` outcome; an unhandled ask is now refused with `reject_once` when offered and cancellation otherwise. Omission means `ask` (`DEFAULT_PERMISSIONS`). Inheritance replaces the whole object, in the stated order. Rules, exact-command matching, the `bash -lc` wrappers and the deny-then-ask-then-allow order match `matcher.ts`.
- **Schema.** I wrote a real schema-16 database with the installed 0.12.1 and opened it twice with alpha: schema **21**, the conversation readable, and the new pieces exactly as listed (channel-intent tables and `controller_kind` from 17, worker assignment and delivery tables from 18, `workers` from 19, the `role` column, and `native_metering_proof_json` from 21). The 0.12.1 code then refuses the migrated file ("SQLite agent schema 21 is incompatible with 16; recreate the database"); the note's advice to restore the backup instead is right.
- **Errors and exports.** `HarnessUnavailableCode` is exactly `not_running`, `failed`, `stopped`, `open_timeout`, `start_failed`, `reopen_failed`; `channel_retired` is a `HarnessClientError` code raised by `resumeChannel` during a pending retirement (the note's wording is fine). Every name the note lists exists in alpha's exports. `ConversationPersistenceContext` gains only the optional `role`; `LaunchKind` gains `"native-harness"`; `AgentConversation.connection` is a `ConversationController` and `harnessConnection()` returns `HarnessController | null`; `OpenOwnedAgentConversationResult.providerSession` gains `"deferred"`; `host.pendingChannelChanges()` exists and reading the channel records of a durable host throws; orchestration requires both worker repositories and message capture `content`.
- **Stop and close** (a taken prompt keeps the cancelled result with the partial text) match what I measured in the R6 reviews.

**2. agents-core.** In a scratch copy (sources copied, `node_modules` linked, only `@qlairoslabs/acp-client` repointed, same dependency set for both): **112 baseline errors; 125 with `510e2a7` (and 125 with `da4e0c0`)**; the 13 added are 9 `defaultPermission`, 1 launcher kind, 1 `currentClient` narrowing and 2 branded-context errors in `acp-contract.test.ts`; applying the documented edits (all six rows) returns **exactly the baseline, byte for byte**, on both packages. That confirms cod2a's numbers and the type-level instructions; finding 1 is the runtime gap.

**3. The guide.**

- **Stale material is gone:** no `defaultPermission`, no "scripted harness used for offline development", no `currentClient`, no `AgentController` example anywhere in `CONSUMER_GUIDE.md`; the heading "Native harness conversations (experimental)" is kept.
- **Examples:** of the 75 `ts` blocks, 7 are new or changed. The five self-contained ones (permissions, cancellable startup, native open, native prompt, worker pool) **compile with zero errors** against the source, and I **ran them offline**: the approval demo prompted an echo ACP agent (`answerPermission` of an unknown id returns `{ accepted: false }`), the lazy reopen stayed disconnected, an aborted `AgentSession.create` returned null on `ConnectionCancelledError`, the native example ran with a scripted model (the `lookup` ask was granted by `approvalResponder`, the result `"Status is ready."`, receipts `delivered` and `seen`), and the worker pool opened with `workers` and `orchestrator` present and `check` of an unknown handle rejecting "unknown active worker". The other two changed blocks are fragments that depend on the surrounding session manager (the `permissions` property is valid in both). The four old blocks that don't parse are ASCII diagrams, unchanged.
- **Claims checked in code:** the permission timeout default (300,000 ms), the range (positive integer below 600,000), `expiresAt` only for a consumer wait, the resolution `by` values, the microtask resolution event, the harness's ten-minute approval limit, native asks using `permissionRule` and the default only, the orchestrator keys (`workers.adapterId/cwd/limit/idleStopMs`, `ownerPolicies`, `defaults`, `policies`, `delegation`, `workerPermissions`), the ten-minute idle default, `no_worker_free`, `assignment: "new"`, and the five `agent.workers` methods.

Native `billing_required` stays refused and nothing claims between-turn support. All links in the guide and the note resolve in the repository and the three anchors exist.

## Is the required-member list complete?

I re-diffed the public surface (public members only) of `0.12.1` against `b8d627b`, with three separate passes: object types, tagged unions and string-literal unions.
