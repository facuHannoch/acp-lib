## Proposed brief

### Step 1 — Withdraw a native prompt

Keep `conversation.withdraw(id)` and `handle.withdraw()` synchronous for local cancellation. Recommend additive `conversation.withdrawAsync(id)` and `handle.withdrawAsync()` for a native input beyond the local queue. Both entry points share one implementation. The async answer is true on confirmed withdrawal, false if the turn took the input or there is no outstanding message, and rejects with the existing request error when the outcome is unknown. Keep a pending prompt eligible for its real outcome after a request failure. Overlapping calls for the same ID can share an answer. Once the settled prompt is gone, a later call returns false. Keep the async methods additive.

Identify the send boundary in the host, which records `saved` before start and `unknown` via `markSent` before calling `client.push`. The session's `sending` state alone cannot tell whether bytes left. Cancel locally before the write, including while the dispatch hook or launch is held. Fence the continuation so it cannot push a locally cancelled item. Once the push is issued, use the live connection even if the push response is pending. The stdio server dispatches concurrently. Treat `not_found` after an attempted push as unresolved until acceptance or reconciliation supplies evidence for a retry. Avoid queuing withdrawal behind the entire acceptance RPC. A late push response must not undo a confirmed withdrawal. On loss, use the existing bounded request response and the authoritative reconciliation view. Persist a withdrawing flag in the existing submission records before the withdraw RPC. A pending withdrawal blocks push replay. Keep it across harness reopen and across Agent reopen with file-backed submission records. The default memory records survive only a harness restart, even on a SQLite-backed Agent. R6 does not introduce SQLite submission persistence. If neither the response nor the view proves withdrawal, leave the prompt eligible for its real outcome. Use the existing cancellation result, with one `message_withdrawn` for an explicitly withdrawn prompt. Audit the separate `interrupt({ clearQueue })` path, which also drops accepted-unclaimed entries today. For native, keep accepted inputs following their backend outcome when interrupt clears the local queue. Stop and close attempt withdrawal of submitted, unclaimed input before interrupting the active turn. A shared one-second deadline bounds that effort. They then reject only submitted inputs that were never taken with `NativeInputStoppedError`. A taken prompt keeps its cancelled result and partial text from the running turn. Input can still run if take has won or withdrawal cannot reach the host. Document these choices and cover each by test.

Wire assumption confirmed by haurness-l. Concurrent push and withdraw have no per-channel ordering guarantee, and the harness keeps no tombstone for an unknown item. For a committed inbox item, withdrawal is atomic against take. A `not_found` response means there was no committed match on that channel at lookup time. An unresolved push may still commit later. Only `withdrawn` confirms cancellation of an accepted item, and `taken` leaves the prompt following its turn. Suppress replay once the intent is recorded. On reconnect, reconcile and retry within a bounded attempt using the original channel and item ID. Use a controlled peer for the lookup-before-commit race, without relying on stock-server overtaking.

Gate with an offline real harness for an accepted steer waiting in the inbox and for a take winning the race. A held running tool provides an admission boundary. Use protocol barriers for a push written but its acknowledgment held, a withdrawal committed but its response lost, and a late push response. Verify no run for a cancelled input, the original turn settling a taken input, one prompt settlement and withdrawal event, and no orphan waiter or retry. Cover pre-write cancellation at the local queue and during dispatch/start, plus timeout and reconnect without false confirmation. Preserve the ACP and generic controller contract, including the tests of synchronous local withdrawal.

### Reopen regression — ship with withdrawal

Keep the backend-supervision guard. Exercise the normal session supervisor with tiny configured first-output, next-output and tool limits and a tracked native turn. Hold the replacement connection at an explicit launch or reconcile barrier after the first connection dies. Confirm the turn remains pending past the client limits. Release the barrier and check that reconciliation settles it exactly once from harness evidence. Exercise the bounded exhaustion path and check that it fails with `HarnessUnavailableError` and `reopen_failed`. Existing ACP tests remain the gate for client-side stall detection. The elapsed-time assertion is part of the behaviour under test. Use events for launch, loss and reconciliation synchronisation and keep all deadlines bounded.

### Step 3 — Expose item milestones to conversation subscribers

Extend the existing controller event path and emit an additive `items_receipt { turnId, itemIds, milestone }` on the conversation subscription. Use the session turn ID form used by `turn_started` and `turn_completed`. The IDs are harness item IDs and may include external notices. Advance each item only once per milestone using the controller's existing lookup, so repeats cannot cause a second event or regress Seen to Delivered. Forward while the controller knows the turn, including held turns before preparation. Keep membership and settlement on `turn_started` and `turn_took`. Keep `receiptOf` for lookups and keep `message_delivered` semantics and serialization intact. The receipt is a live event. Reconciliation and item-status reads remain the sources for history. Cover the public addition in the changelog and guide, and check exhaustive switches. The event has no synthetic transcript record or Agent-wide record event.

Gate with controller tests for repeat, mixed new and known IDs, and out-of-order milestones, and through a real harness with a queued or steered input taken into a turn. Assert conversation routing, turn and item IDs, milestone order, one completed result and consistent `receiptOf`. Test a held turn and reconnect without promising replay of a receipt absent from the live subscription.

### Step 4 — Verify the consumer text path over stdio

Extend `nativeRig` coverage using the existing scripted step schema and `harness.text: "stream"`. Use a stream with a controllable boundary after a partial reply so the consumer's `onChunk` proves live delivery before the turn ends. A scripted partial reply followed by a held tool supplies the boundary. Check the completed message ID and full committed text in the result and local transcript exactly once. Compare against the default `final` subscription, which receives completed content rather than provisional wire deltas. Preserve the existing controller coverage for suffix completion and by-reference replies. If exercising gap repair in stdio requires a packet filter, use a deterministic test transport and keep the real-child gate focused on the ordinary stream.
