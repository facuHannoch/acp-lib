# R2 grounding — ACP permission requests and matching

Grounded at `a180301` after fast-forwarding `native-integration-r` to alpha. This report covers step 0 of [Brief R2](../11-11-SPEC-native-harness-integration.md#brief-r2-the-permission-setting-and-matcher-acp-side). The [Permissions design](../11-11-SPEC-native-harness-integration.md#permissions) and [automatic-approval rule](../rules/11-13-RULES-permission-auto-approve.md) govern the later steps. This is a documentation-only change. Verification used scripted fixtures.

## Current request path

- The SDK registers `AcpClient.handlePermission` at `src/client.ts:378`. At :971–1008 it converts the request, starts permission accounting, and races the active handler or fallback against cancellation. The `finally` removes the pending cancel callback and emits `permission_ended`. The mapper at :1078–1092 exposes `toolCallId`, title and option triplets, and puts the original request in `raw`. The matcher sees kind and input only under `raw.toolCall` today.
- The old `AgentSession.runPrompt` permission closure is now `src/conversation-turns/recording.ts:161–200`. `runTurn` constructs it at `src/conversation-turns/run-turn.ts:126` and passes it to `prepareTurn` at :147–160. `HarnessController.prepareTurn` at `src/controller.ts:345–364` passes the handlers through to the provider prompt. The recording closure writes Agent-owned requested and resolved permission records around the decision. It calls an explicit prompt handler through `permissionWithAbort`, otherwise `defaultPermissionOutcome` at `src/conversation-turns/record-helpers.ts:67–75`. Combined steer retains the first handler that answers permissions (`src/steering/combine.ts:23–24`).
- A raw or handlerless `AcpClient` request uses `defaultOutcome` at `src/client.ts:1010–1024`. Both fallback implementations default to cancellation. Approval picks `allow_once`, then `allow_always`, otherwise cancels. Selection uses option kinds. The last-resort `allow_always` can write a persistent grant in Claude and remains part of the approved rule.
- The recording handler is also reached by native backend-started turns. `src/native/controller.ts:522–539` currently adapts an approval to the public callback shape, offering `allow_once` and `deny`, with the approval event as `raw`. A configured host-level responder takes a separate route. R2 must keep its ACP matcher out of both native routes. One existing behavior needs an explicit migration decision in step 3. A native per-turn ask without a consumer handler currently reaches the shared fallback, so an explicit old `defaultPermission: "approve"` can allow it. Recommend leaving native policies and prompt/host responders authoritative, keeping an unattended native ask refused, and documenting the removal of that old opt-in rather than applying ACP rules to native requests.

Step 3 is a breaking configuration rename. ## Neutral request and orchestrator seam

Put the neutral request and option types in `src/permissions/request.ts`. Recommend a typed `tool` with optional `name`, optional `kind` and unknown optional `rawInput`, plus title and option triplets. Retain public `PermissionRequest` and its existing ID/title/options/raw surface for prompt handlers during R2. An ACP adapter in the permissions module can project a neutral view while retaining the original packet for current consumers and existing requested records. The session's record serialization explicitly enumerates fields, so it need not copy the new view into the record. `src/client.ts` is 1,092 lines and `src/agent-session.ts` is 4,567 lines at the baseline. Moving the request mapper and duplicate fallback selection into the permissions module gives both files room for the wiring without growing.

R3 can reuse the neutral view for `permission_requested` and use its own request ID, turn ID and expiry at the event boundary. Native can construct the view from the approval event's stable tool name, argument string and offered options, with kind absent unless the producer has a reliable value. The ACP matcher remains out of that path. Preserve the original tool-call and native approval IDs for record linkage and responses. ACP abort accounting and native approval close signals already exist and should remain the lifecycle sources.

The orchestrator needs a pure **match-to-level** API accepting a neutral ACP request and an already selected setting. It can extract `worker:` entries and strip that prefix once before calling the matcher. The orchestrator owns assignment context and merges decisions across the applicable policy names; the matcher need not read harness policy configuration, understand worker routing, or emit approval events. Keep option selection separate so O4 can forward ask outcomes and restrict presented `allow_always` options when required. The ordinary ACP setting only needs deny, ask and allow. Preserve an orchestrator extension point for `ask_agent` and the same most-restrictive rule reduction rather than conflating it with ordinary ACP ask. No orchestrator caller is required in R2.
