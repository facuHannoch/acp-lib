## Persistence and transaction grounding

[backend.ts](../../../../../src/persistence/backend.ts) L723–734, L764–802 gives the reuse pattern: optional `identity?` in `PersistenceScope`, `capabilities.identity` on the backend, and asynchronous repository methods. `PersistenceBackend` extends the scope, while the callback receives only `PersistenceScope`. [sqlite-backend.ts](../../../../../src/persistence/sqlite-backend.ts) L187–196 sets the identity flag; L331–363 constructs scoped repositories with the supplied write runner. R1 should put `channels?` on the scope and wire it into both root and transaction scopes. Backends with neither capability nor repository keep the existing fallback.

SQLite `transaction(work)` L281–298 queues one writer on `writeTail`, issues `BEGIN IMMEDIATE`, awaits the callback using repositories that run inside that transaction, and commits or rolls back on an error before commit. Canonical record notifications follow commit. The ordinary root repository write runner opens its own queued transaction (L417–435). Inside the delete transaction, use its scoped repository for both retirement and deletion. Awaiting a root write from inside that callback can wait on its own queued transaction. Native RPC and host delivery must happen after commit. The current read pattern can issue queries on the same SQLite connection without the write queue, so **host delivery reads must also be kept out of an uncommitted transaction's view**. Give the channel repository's root read path a committed-read boundary, such as sequencing these reads on the existing queue, while its transaction-scoped reads use the transaction directly.

[sqlite-schema.ts](../../../../../src/persistence/sqlite-schema.ts) is at version **16** (L5). Migration uses `schema_migrations`, not `PRAGMA user_version` (L606–615). Bumping the constant to 17 requires explicitly admitting existing version 16 in the compatibility check. Reuse the migration transaction and its version bookkeeping (L625–700). The existing multi-repository rollback test and schema-15 upgrade test are patterns for the R1 rollback and real on-disk 16→17 upgrade cases. Keep the version allocator durable even when no pending row remains. An acknowledgement for a previous version must never match a later desire after a clear or restart.

## Recommendation for review

**Make the host's channel records path asynchronous.** Put the repository adapter in its own module. Before wiring it, extract the channel intent scheduling and delivery code into a focused module so `host.ts` stays at or below 984 lines. Extract the manager's native delete/retirement transaction helper before adding the transaction path so the manager stays at or below 1,098 lines. The existing host queue and live operator calls should remain the delivery mechanism. Keep the submission half synchronous and reuse the existing memory implementation when `channels?` is unavailable. Separate the channel adapter from submission storage so a supported backend has one channel intent writer.

A mirror would retain synchronous host lookups, but would need hydration, commit notification, rollback handling, acknowledgement reconciliation and refresh when a transaction writes an intent without going through the host. For example, publishing the retirement to memory before the soft-delete transaction commits lets the host deliver a retirement even if the transaction rolls back. A mirror would have to update only after commit or reload from the repository after commit, with delivery held until then. The async design uses no mirror: both writes use the transaction scope, and the manager schedules host delivery only after that transaction resolves successfully. A rollback produces no queued delivery and leaves no retirement visible to the host. The async adapter plus extraction keeps `host.ts` from growing and removes this source of drift.

Two ordering constraints need explicit tests at the async wiring step. Register the per-channel edit order before introducing an await so a later push cannot overtake it. At startup, preserve the cutoff semantics when the post-open scan awaits storage: serialize the scan and transition to running against intent commits/enqueues so an edit committed during the scan is neither missed nor placed after a newer input. The current `#afterOpen` scan is synchronous immediately after running is published (host L357–361); making that scan async without a barrier changes the guarantees. For deletion, enqueue delivery for the already committed intent without calling `desire` again or minting a second version.

For step 2 review, decide the public compatibility shape. Both host record factories and `NativeHostRecords` are exported (index L268–269), and callers inspect `host.records.pendingChange(s)` synchronously today. Prefer a distinct async channel surface, or a widened channel contract with narrower sync return types for the legacy factories, over exposing a stale second writer. Under a durable backend, explicit `harness.records` may still supply submissions, but must not override the repository for channel intents. Existing file-store pending changes do not migrate under the written brief. Clarify whether to reject, import, or document a transition for that configuration before switching its channel authority. Also decide how the operator suspend/resume conveniences enter the durable intent path while preserving their existing live status contract. These are review points for the wiring steps, not changes in this report.
