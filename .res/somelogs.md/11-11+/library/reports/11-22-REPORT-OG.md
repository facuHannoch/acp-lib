## Worker delivery and Gate 3 handoff

Schema 18's `worker_assignments` stores the assignment ID, `worker_id`, original and current destination, causal message ID, writer owner, eventual operation and final record IDs, originating and contributing names, staged result/notice and delivery state (`sqlite-schema.ts:5–24`). `workers.last_conversation` is worker status and the default for a future assignment. Native and ACP delivery resolve the committed assignment destination, or the payload's frozen destination once staged. A redirect notice goes to the former assignment destination captured before the redirect.

| Boundary | Existing call or proposed Gate 3 entry |
| --- | --- |
| Reserve | O3a calls `reserve({ assignmentId, workerConversationId, messageId, destination, originatingPolicyNames, contributingPolicyNames })` from `beforeDispatch(messageId)`. Use the callback invocation ID for the new assignment. `reserved` permits this new dispatch. `existing` means the original binding matches; it does not prove dispatch happened and grants no authority to dispatch again. `conflict` rejects dispatch. The current SQL checks worker/message/original destination/originating names, with uniqueness on worker/message too. Put any required related writes in the same scoped transaction. |
| Steer and redirect | Existing `addContributingPolicies(id, names)` and `redirect(id, destination)` both return false for missing or staged rows. Compose redirect destination, contributing names and worker metadata in one transaction; respect a false result and retain an already staged payload. Originating names remain immutable. Terminal commits also union names from causal reserved bindings. |
| Terminal evidence | The production lifecycle calls `recordFinal(workerId, operationId, messageIds)` or `recordFailure(workerId, operationId, messageIds, failure)` on the transaction's scope (`persisted-lifecycle.ts:177–196,271–275`). Do not repeat either call from the orchestrator. The final path binds the latest captured completed assistant record and policies atomically with those records. If no saved result exists it stages a known failure. Known failure/interruption stages a safe bounded reason and notice inside that terminal transaction. `WorkerAssignmentOutcome` distinguishes result, failed, interrupted and uncertain. A stall is failed; forced stop or a cancelled result is interrupted; inherited unfinished work without reliable final evidence is uncertain. Partial effects may exist. |
| Stage and discovery | After the terminal transaction commits, Gate 3's handoff worker calls `stage(assignmentId)`. It does the same on startup for recoverable records discovered by its scan. It returns an existing stage idempotently, freezes a result and notice from durable evidence, stages uncertainty for an abandoned prior owner's unfinished work, and returns undefined for a missing ID or a current owner's live unfinished operation. Success therefore has two durable boundaries, final record and subsequent stage transaction. Production subprocess tests already cover loss on either side of final evidence, and repository tests cover stage rollback, repeat, redirect and transitions. |
| Flush ownership | Proposal for Gate 3 to confirm: committed repository state is authoritative. Use a post-commit wakeup for the assignment ID (e.g. a handoff-owned `assignmentCommitted(id)` entry) to avoid waiting for reconnect after live completions. Existing `agent.events` is insufficient alone because some terminal outcomes have no captured assistant record. Gate 3 needs repository-backed discovery of inherited and unstaged assignments and pending notices by destination or stable cursor, plus a read-only way to select the latest outcome for worker status, since the current contract only reads by ID. Startup scans are the recovery backstop for missed wakeups. O1 through O5a call neither `stage`, `transitionDelivery` nor the native flush. O3a verifies reservations and terminal evidence through read APIs and delivers the independent ACP port. |
| Flush and retries | Gate 3 owns `HarnessClient.notify({ channel: delivery.destination, notice: { id, text, source, policyNames } })` in the host's per-channel queue, behind pending channel changes. It flushes on open after R1's cutoff/change reconciliation and on live stage, retries a lost ack with the exact same payload and ID, and requeues on session/channel resume or confirmation of the earlier intent. Use `transitionDelivery(id,{from:"pending",to:…})` with delivered for either accepted receipt, blocked_policy for invalid policy, failed_destination for missing/retired. Keep suspension, earlier unresolved change or ambiguous ack pending. Expose explicit policy retry through the handoff owner via `{from:"blocked_policy",to:"pending",explicitRetry:true}` and reschedule. Keep the result inspectable on block/failure. Surface a stable-ID payload conflict explicitly, with its terminal treatment agreed by Gate 3. |

**Contract gaps for Gate 3 and the spec owner.** The current staged source is the worker conversation ID, while the design asks for its handle. Resolve or persist the source label before staging so retries use identical payload. Current result text joins captured completed assistant messages through the final record, while Flow 3 says “final message”; agree the product projection before O3b. The repository currently stages interrupted notices unconditionally and can stage the old ACP operation at a steer boundary. It has no API to transfer the same assignment's causal message binding to a successor run, suppress an explicit-stop notice durably, or stage a separate redirect notice to the previous destination. Agree the durable handling before O2/O3a/O5a. In particular, `redirect` and `addContributingPolicies` only mutate pre-stage fields, and cannot substitute for successor-run correlation. O3a's independent ACP delivery also needs an agreed routing boundary so Gate 3's native scan never sends an ACP destination to `channel/notify`.

The first supported proof path is a file-backed, Agent-owned ACP worker with message capture sufficient to retrieve text. Known terminal evidence stays recoverable without provider redispatch. Review whether to require the capture setting in the pool, since a successfully completed prompt can intentionally omit saved text under other capture settings.

## Harness wire and actor

- **Callback policy amendment.** `src/native-harness/src/index.ts:89,125–145` takes names from inputs already attributed to the turn, including inherited notice names. The dispatch-time snapshot authorizes the tool and is reused after approval for the callback, with `__legacy_allow` omitted. `interfaces/client.ts:78–90` rejects missing, duplicate, blank and internal names in both transports. `src/native/functions.ts:28–37,112–115` forwards a copied `policyNames` array along with invocation ID, channel, turn, tool and signal. Tests in `src/native-harness/test/tools-protocol.test.ts:312–405` exercise inherited names, pending/taken inputs, approval, argument spoofing, empty lists and malformed inputs.
- **Actor and catalog.** `NativeFunctionContext.channel` identifies the native conversation; `invocationId` is formed from harness turn ID and tool call ID. The worker rules map belongs to the Agent's active harness configuration, captured per open, with explicit empty names using configured defaults and unknown names failing closed. There is no sender field on the callback. Build sender attribution from authoritative taken-item evidence exposed via the host's observe/reconcile or retained receipts, never model arguments. Agree which actor represents multiple participant inputs or notice-only turns and how the lookup is bound to the actual invocation's authorization snapshot; a later observation may already include newer inputs. Authorize via the frozen callback names independent of display sender. `AgentHarnessConfig.functions` already has a tool registry; the host announces handler names in `initialize` and supplies `functions.catalog()` on `session/create` and `session/open` (`host.ts:394–405,505–525`). Merge fixed delegation entries with consumer tools and define collision handling. Update the spec's `session/load` reference and retain guidance in tool descriptions.
- **External notices.** `channel/notify` is implemented in the harness server at L299–316 and exposed as `HarnessClient.notify` at client L130. Storage checks identical-ID receipts before admission, then requires a running session and an open existing channel for a new notice (`state/storage/engine.ts:423–492`). Signature covers kind, destination, source, text and the inherited policy set. The harness commits before acknowledgement and only pumps a new item. Timeline, attribution and archive preservation are implemented. `src/native-harness/test/external-notices.test.ts` covers detached delivery/steering, policy composition, conflict and a lost ack across reopen with exactly one take. The public acp-client host offers status, observation, channel/session control and timeline; it neither exposes nor calls a durable notice sender at this base, and `channel/notify` is absent from its required-method list. Gate 3 can condition its compatibility check on configured delivery.

## O4 forwarding seam and file budget

The worker prompt gets the assignment-bound `onPermissionRequest`. Final worker allow/deny selects the ACP option locally. Ask forwards the neutral request and the worker's abort signal to the **giving** conversation, with stable worker handle/conversation ID as the source and explicit worker operation or assignment correlation. Filter `allow_always` for non-owner asks before publishing the options and use that same filtered list for answer validation. On the worker side, ensure the assignment handler reaches R3's ask branch even if the Agent normally applies a final permission level; make the worker policy local to its conversation with no inherited final-level shortcut.

Add one internal entry to `ConversationPermissions` in `src/permissions/conversation.ts`. It should register an external ask in the receiving conversation's existing pending-ID map and emit `permission_requested` with optional worker source metadata. Forwarded delivery has its own correlation and no local active turn. Define the event turn field for this case explicitly, preferably as optional with a worker turn ID in the source when available. The giver's `answersPermissions` and ingress-relative consumer budget determine whether the request waits; no answerer means immediate refusal. Use the worker ACP request's existing ingress timestamp when available. Resolve the forwarded entry with the chosen original ACP option ID back to the worker's waiting handler, using the same `answerPermission` claim path. Expiry resolves through the deny selection, giver stop or worker abort closes the entry, and a late answer is rejected. The giver's unrelated turn ending must leave forwarded work alone. Reuse the existing one-shot cleanup and the requested-before-microtask-resolution ordering. The worker still owns its permission records and wire response. Restart forgets the in-memory ask and never replays the work.

Recommend **one reviewed O4 exception** to the no-edit rule for `src/agent-session.ts`: a small internal forwarding delegate parallel to `answerPermission` around L1911, passing the same runtime configuration into the existing private coordinator. Keep the work in the coordinator and keep the session within its baseline size. The public event union will gain the worker source variant. Without this seam the giving object has neither a callable entry for its coordinator nor an answer slot for a forwarded ID. O1/O2/O3a/O5a/O3b/O5b/O6 can keep `agent-session.ts` untouched. Align the Code plan, Common and Acceptance no-edit statements with the revised O4 order before implementation.
