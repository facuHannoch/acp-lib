## Questions for haurness-l before implementation

1. For a proof-budget `storage_failure` during an executable open/create batch, what is the rollback boundary? Can earlier channel changes or reminder receipts commit, can later entries run, and can due work run before the error is returned? Is the failed entry identified in error data? Can a replay rely on the original request being accepted after a create partially succeeded? Confirm whether earlier successful receipts are replayable while the failed entry has none. This decides whether retry can be narrowed to one entry or must reuse the exact batch.
2. How should the first executable open of a new acp-client process stage previously accepted routine intents before it knows the effective guard? Propose staging after initialize if the saved evidence applies to the same session, or if the request binds a configured guard before applying changes. Confirm fail-closed behavior for missing/stale evidence. Opening without an owed pause or cancellation can permit due work before the edit.
3. What is the exact public wire type for the version-migration `invalid_schedule` disposition? The contract describes a durable notification with old/new versions and `invalid_schedule | proof_budget` cause. The documented `routine_disposition` range shape has five different reasons. Confirm event name, fields, row names for canonical zone and data version, and whether any stable identity is provided for dedupe.
4. For ordinary dispositions, does a tuple of session, reminder, endpoints, count and reason uniquely identify an event? Are they live-only under 0031, and can clients read historical dispositions or get a row revision to associate a range with its updated count? Confirm event order relative to the associated `reminder_changed` and `reminder_fired`.
5. Confirm how a routine schedule with inclusive `until` before the first possible occurrence is handled, and whether the normalized interval row returns an explicit `startAt` when the request omitted it. Confirm whether a replacement whose earliest candidate is at or behind the processed-through fence rejects, or advances through that fence before checking the remaining bound.
6. Confirm the error data for `invalid_config` and how a mixed-version host should detect support for `limits.unattendedTurns` before sending it. If a user explicitly configures a guard on a one-off peer, prefer reporting incompatibility over silently dropping the setting.
