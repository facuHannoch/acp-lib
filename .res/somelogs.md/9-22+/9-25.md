This is not as simple as just doing 
session/list
session/load SESSION_ID

Because we have a whole system of conversations and summaries, and an identity.
The user could use the controller, but that is quite low-level.

So the ideal thing would be to allow to kind of "adopt" a session load.
Now, there is a question, which is what happens with the summaries, the identity, etc.
Because even if we avoid the problem that allowing to load a session on an existing conversation could bring, suppose I create a new conversation, and then I load a session of 500 messages.
What should happen ?
We kind of already thought about this problem, but it was in the context of
_What if I can't load the existing session?_
And then we came up with the concept of summaries.

Now, this is different. We solved that one by having periodic summaries. We can't do that here.
Maybe we don't need to, and this is one option: dont try to put this into memory. Like, we could make do a handoff, or not even, just ask the model for a summary and store that.
There is one thing that we have now that we didn't on the other case, which is that we can ask the model. Here the model is reachable (otherwise there would be no load). So maybe there is no problem of large transcripts, because we can use the model knowledge there.
So, there we have two options:
1. session/load, not create a summary. There is a problem though: this will be taken as a new conversation, and the model will attempt to create a summary with only the first response (the only one stored), which is mmisleading. So we disable the summaries here, or...
2. session/load, we ask the model to create a summary. While it solves the problem of the summary, it also forcefully writes on the user's chat. Not only that but it makes them wait. Both could be acceptable, given that the summary is not really something that changes the memory, and the wait is maybe understandable
