## Where committed-record notifications originate

The persistence backend is the only layer that knows whether a transaction actually committed.

The bus must not be called directly from each producer because records are written from several places:

- live prompt processing;
- protocol capture;
- metering;
- checkpoint completion;
- internal inference strategies;
- future error recording;
- potentially persistence extensions.

Manually adding `bus.emit()` after every current write would inevitably miss background writers.

The persistence contract therefore needs a commit source:

```ts
export interface ConversationRecordCommit {
  readonly records: readonly ConversationRecord[];
}

export interface ConversationRecordCommitSource
  extends Subscribable<ConversationRecordCommit> {}
```

For SQLite:

- Collect records appended during a transaction.
- Commit the transaction.
- Publish one immutable batch after `COMMIT`.
- Publish nothing after rollback.
- Direct `append()` and `appendMany()` use the same implicit-transaction behavior.

The current SQLite backend already collects committed records for persistence-extension callbacks. That collection can support the new commit source, but the extension callback itself should not be reused as the public bus. Extensions and consumer observation have different failure and ownership semantics.

## Custom persistence backends

Making a new commit source mandatory would immediately break existing custom backend implementations.

A compatible approach is:

```ts
interface PersistenceBackend {
  readonly recordCommits?: ConversationRecordCommitSource;
}
```

When opening an Agent:

- If the backend provides a native commit source, use it.
- Otherwise, wrap the backend in an observable decorator.
- The decorator intercepts `records.append`, `appendMany`, and transaction-scoped record persistence.
- It publishes only after the underlying operation or transaction resolves successfully.

Accepted limitation: writes made directly through the original custom backend outside the Agent cannot be observed by the Agent’s bus. All writes made through `agent.persistence` are observable.

SQLite should implement the native source because it can provide exact commit semantics.

The conversation manager checks its existing live map:

- Notifications are process-local and non-durable.

- Listener exceptions are logged and isolated.

1. Correct provider-session persistence.
2. Build the generic committed-record event bus.
3. Add curated error records and deliver them through that bus.

The first change is conceptually simple, but it is more than adding one variable.

## What stays in memory

We already keep the provider ID in memory:

```ts
private _internalSessionId: string | null;
```

That remains available for:

- prompting;
- configuration;
- commands;
- tool/MCP setup;
- showing the current live provider ID;
- stopping the provider.

What changes is whether that ID has been written to the durable `provider_sessions` table.

Internally, we need a small runtime state such as:

```ts
type ProviderAttachmentPersistence =
  | { kind: "pending"; internalSessionId: string; activatedAt: string }
  | { kind: "persisted"; internalSessionId: string }
  | { kind: "absent" };
```

This does not claim the provider session is durable. It only says whether our database contains it as the preferred future continuation candidate.

A boolean could technically work, but the structured state is safer because session IDs can change through recovery, handoff, or switch.

This state does not necessarily need to become public API in v1.

## Initial creation flow

The logical conversation remains durable immediately:

```text
create agc row
→ session/new
→ keep internalSessionId in memory as pending
→ return AgentConversation
```

At this point:

```ts
conversation.internalSessionId // provider ID is available
await persistence.providerSessions.active(conversation.id) // null
```

When the first prompt completes successfully:

```text
provider responds successfully
→ begin SQLite transaction
→ append assistant message records
→ append active provider-session mapping
→ commit
→ mark in-memory attachment persisted
```

If the conversation stops before that:

```text
stop provider
→ discard in-memory pending ID
→ leave logical conversation in SQLite
→ leave provider_sessions empty
```

Opening that logical conversation later starts a fresh provider session rather than attempting to load the discarded ID.

## What counts as successful

We should use a conservative boundary:

- A prompt must have been dispatched.
- The provider must return a settled `completed` result.
- The corresponding canonical assistant records and provider mapping must commit successfully.

These should not confirm the mapping:

- queued prompt cancelled before dispatch;
- provider process crash;
- connection loss;
- prompt returning `error`;
- interrupted or cancelled turn;
- successful provider response followed by failed local persistence.

The last case is important: the provider may possess the conversation, but our database does not safely describe it.

## Atomic persistence matters

We should not do this:

```text
persist assistant response
→ process crashes
→ persist provider ID
```

Nor this:

```text
persist provider ID
→ process crashes
→ persist assistant response
```

The first completed response and provider mapping should be committed in the same SQLite transaction.

That gives us a useful invariant:

> If an active provider mapping exists for a newly created provider thread, the canonical timeline also contains the completed turn that justified retaining it.

The user message is already persisted before dispatch and can remain a separate transaction. That correctly records an interrupted prompt attempt.

## Where the change belongs

The existing `deferProviderSessionPersistence` flag should not become a public consumer option. This is a correctness rule, not a selectable policy.

Instead:

- New provider sessions start pending by default.
- Loaded provider sessions start persisted because the mapping already exists.
- Recovery-created sessions start pending and become persisted after the recovery seed succeeds.
- The private recovery-only flag can then disappear or be replaced by the common attachment lifecycle.

The existing recovery path already demonstrates most of the desired ordering.

## Initial implementation impact

For ordinary SQLite conversation creation, the change is moderate:

1. Stop calling `persistProviderSession()` immediately after `session/new`.
2. Retain the new provider attachment as pending.
3. Give `PersistedConversationLifecycle.afterPrompt()` enough attachment information to commit it.
4. Commit the assistant records and pending provider mapping together.
5. Clear the pending state only after the transaction succeeds.
6. Let `stop()` discard any remaining pending attachment.
7. Update identity-delivery reset ordering so it occurs before the first successful delivery cursor is committed.
8. Add deterministic lifecycle tests.

That is not a rewrite.

## Why the complete change is larger

The invariant must eventually cover every fresh provider thread, not only initial creation.

### Recovery

Already mostly correct:

```text
new session
→ recovery seed prompt
→ persist provider mapping
```

This should be folded into the common lifecycle rather than remain a special flag.

### Handoff and switch

These currently activate/persist a newly created target too early.

The correct behavior is:

```text
create target provider session
→ target is pending in memory
→ successfully prompt target
→ atomically activate/persist target mapping
```

Until that succeeds, the previous persisted provider mapping should remain active. If the process stops, reopening can return to the previous known candidate.

This affects transition semantics: `target_created` is not the same as durably `target_activated`.

### Direct JSONL/v2 persistence

The direct persistent `AgentConversation` path also writes the provider ID into its initial checkpoint before any prompt. Correcting that requires changing how its initial continuation checkpoint represents a live-but-unpersisted provider attachment.

That is more involved than the SQLite Agent-owned path because the provider ID is embedded in the transcript/checkpoint state machine.

## Recommended scope

I would do this in two bounded stages.

### Stage 1: Agent-owned SQLite lifecycle

Cover:

- initial create;
- opening a logical conversation with no provider mapping;
- first successful prompt;
- stop before first prompt;
- checkpoint recovery;
- SQLite provider-session records.

This fixes the active architecture and the Hub problem.

### Stage 2: Every fresh-thread transition

Cover:

- handoff;
- switch;
- direct JSONL/v2 persistence;
- any explicit future `newSession` operation.

This establishes the invariant everywhere.

We should not silently claim the whole library follows the invariant after only fixing initial SQLite creation.

## Required tests

At minimum:

- Creating a conversation persists the `agc-*` row but no provider mapping.
- The live conversation exposes its in-memory `internalSessionId`.
- Stopping before prompting leaves no provider mapping.
- Reopening such a conversation creates a new provider session.
- A completed first prompt persists the provider mapping.
- The mapping and assistant records commit atomically.
- A failed/cancelled first prompt leaves no mapping.
- Successful conversations still reopen through `session/load`.
- Recovery persists its replacement only after successful seeding.
- Concurrent subsequent prompts cannot append the mapping twice.
- Handoff/switch do not prematurely supersede the previous mapping once Stage 2 is implemented.

So: the core fix is moderate and uses state we mostly already have. Making the rule universal across initial creation, recovery, handoff, switch, and legacy direct persistence is a larger but still incremental lifecycle refactor—not a full rewrite.





# Error 1, plan

This should be treated as a provider-attachment lifecycle refactor with two implementation stages. We should write the state-machine spec first, then implement each stage independently and test it before continuing.

## Core invariant

A provider ID can be in one of three local states:

```ts
type ProviderAttachmentState =
  | { kind: "absent" }
  | {
      kind: "runtime_only";
      descriptor: ProviderAttachmentDescriptor;
    }
  | {
      kind: "recorded";
      descriptor: ProviderAttachmentDescriptor;
    };
```

Where:

```ts
interface ProviderAttachmentDescriptor {
  internalSessionId: string;
  adapterId: string;
  mode: AgentMode;
  model?: string;
  acquiredAt: string;
  providerSessionRecordId: string;
  transitionId?: string;
}
```

Meanings:

- `absent`: no current provider thread.
- `runtime_only`: usable by the current process but not selected for future loading.
- `recorded`: stored as the active continuation candidate.

“Recorded” deliberately does not mean “durable” or “guaranteed loadable.”

A newly created provider thread is always `runtime_only`. A successfully loaded provider mapping is already `recorded`.

All provider attachment changes should go through explicit methods instead of the ambiguous current `setInternalSessionId(next, created)` boolean.

## File organization

Add the model outside the large root files:

```text
src/
  conversation/
    provider-attachment.ts
    provider-attachment-errors.ts   # only if needed later
```

`provider-attachment.ts` should contain:

- state and descriptor types;
- pure state-transition helpers;
- guards ensuring the expected ID is being committed;
- no controller or persistence code.

Existing responsibilities remain:

- `agent-session.ts`: live controller and attachment state.
- `agent-conversation-owner.ts`: contract between the live conversation and Agent-owned persistence.
- `agent.ts`: SQLite lifecycle implementation and conversation manager.
- `persistence/backend.ts`: provider-session repository contract.

We should not add another large block of lifecycle logic directly to `agent-session.ts`.

# Stage 1: Agent-owned SQLite creation and recovery

This stage fixes the path used by the Hub and the current SQLite architecture.

## 1. Replace ambiguous attachment assignment

Replace:

```ts
setInternalSessionId(id, created)
```

with explicit internal operations:

```ts
installCreatedProviderAttachment(descriptor); // runtime_only
installLoadedProviderAttachment(descriptor);  // recorded
markProviderAttachmentRecorded(expectedId);
clearProviderAttachment();
```

`conversation.internalSessionId` continues returning the live ID.

All existing assignment sites must be classified explicitly. This prevents a future call site from accidentally treating a newly created thread as persisted.

## 2. Stop persisting immediately after `session/new`

Remove the immediate new-session call at [agent.ts](</home/ffacu/q/apps/libs/acp-lib/src/agent.ts:841>).

The creation result becomes:

```text
conversation row: persisted
provider process: running
internalSessionId: available in memory
provider_sessions row: absent
attachment state: runtime_only
```

Loaded conversations remain `recorded`, since their mapping already exists.

## 3. Carry attachment information through prompt completion

Extend the internal owner lifecycle input:

```ts
interface OwnedPromptCompleted {
  // existing fields
  readonly providerAttachment: ProviderAttachmentSnapshot;
}
```

The result from `afterPrompt()` should acknowledge whether the attachment was recorded:

```ts
interface OwnedPromptCommitResult {
  readonly recordedProviderSessionId?: string;
}
```

The conversation only changes `runtime_only → recorded` after receiving that acknowledgement.

This expected-ID acknowledgement prevents an old completion from confirming a subsequently replaced provider thread.

## 4. Commit the first successful turn atomically

For a `completed` result, one SQLite transaction should:

1. Append the final assistant message records selected by capture policy.
2. If the attachment is `runtime_only`, append its `provider_sessions` row.
3. Reset the identity-delivery cursor for the new provider context if required.
4. Enqueue selected audit observations.
5. Commit.

After commit:

- update identity;
- acknowledge the attachment as recorded;
- schedule checkpoint generation.

If the assistant-message capture level is `none`, the provider mapping still needs to commit. Record capture must not suppress attachment persistence.

Cancelled, failed, or interrupted results persist their normal records but do not record the provider mapping.

## 5. Handle lazy provider creation

`session/new` can fail during startup—for example, before authentication—and later succeed during the first prompt.

Therefore, staging the provider descriptor only in `AgentConversationManager.start()` is insufficient. `AgentConversation` must update its attachment state whenever the controller acquires a new session ID, including lazy creation during `prompt()`.

The descriptor’s `acquiredAt` should be captured at that moment, not at prompt completion.

## 6. Stop behavior

Stopping a `runtime_only` attachment:

- stops the process;
- clears the in-memory attachment;
- writes no provider mapping;
- retains the logical conversation and any canonical records already written.

No explicit deletion is needed because the mapping never existed.

## 7. Fold recovery into the common lifecycle

Recovery already follows the correct ordering:

```text
create provider
→ seed recovery prompt
→ persist mapping
```

Replace `deferProviderSessionPersistence` with the common `runtime_only` state.

After a successful recovery seed:

- persist the pending descriptor;
- supersede the previous active mapping;
- mark the live attachment recorded.

If seeding fails, retain the previous active mapping and discard the new runtime-only attachment.

## 8. Stage 1 persistence changes

No SQLite schema migration should be necessary.

`provider_sessions` retains its current meaning:

> Provider sessions selected as future continuation candidates.

Existing databases keep their existing mappings. We should not guess whether historical rows had a successful prompt.

- Configuration commands work before the first prompt.
- Stop before prompt leaves `providerSessions.active()` null.

# Stage 2: Handoff, switch, reset, mode changes, and direct persistence

This stage establishes the invariant across every provider-thread creation path.

It is larger because transitions currently treat `target_activated` as both:

- active in the running process;
- selected durably for future continuation.

Those meanings must be separated.

## 1. Keep the previous recorded mapping until target confirmation

For handoff and switch:

```text
create target controller
→ target attachment is runtime_only
→ configure target
→ seed/prompt target
→ commit target mapping
→ supersede previous mapping
→ stop previous controller
```

The previous mapping must not be deactivated when `session/new` merely succeeds.

For cross-adapter and same-adapter transitions, create a separate target controller. Reusing the current controller’s `newSession()` makes rollback unreliable because it replaces the active thread inside that controller before the target is proven usable.

## 2. Separate target creation from durable activation

Current transition events are:

```text
started
target_created
target_activated
completed
```

The revised meaning should be:

- `target_created`: provider returned an ID; target is runtime-only.
- `target_activated`: target completed a provider turn and became the recorded continuation candidate.
- `completed`: handoff/switch operation finished.

Do not write `target_activated` before the seed or target prompt succeeds.

This matches the current transcript reducer, where `target_activated` changes authoritative continuation state.

## 3. Default handoff and switch

Default handoff generates and sends continuation context. That seed prompt is sufficient evidence.

The correct order becomes:

```text
generate summary on source
→ create target
→ configure target
→ send continuation seed
→ if completed:
     activate target durably
     stop source controller
     complete handoff
→ if failed:
     stop target
     retain source controller and mapping
     fail handoff
```

An optional target prompt happens after target activation unless we deliberately decide that it must also succeed. I recommend using successful continuation seeding as the confirmation boundary; otherwise a valid target would be discarded because an unrelated first instruction failed.

## 4. Reset without a prompt

`reset({ continuation: none })` can create a target without sending anything to it. It therefore cannot become recorded immediately.

Recommended behavior:

- Switch the live conversation to the runtime-only target.
- Keep the previous recorded mapping as the restart fallback.
- Return that the reset target is runtime-only.
- The first later successful user prompt records the target and supersedes the old mapping.

Add an explicit field to `HandoffResult`:

```ts
readonly providerAttachment: "runtime_only" | "recorded";
```

This reports local persistence state, not provider durability.

If `reset()` includes `targetPrompt`, a completed target prompt can record the target immediately.

## 5. Pending transitions across the first later prompt

For a prompt following a promptless reset, the runtime must remember:

- original transition ID;
- previous recorded descriptor;
- target descriptor;
- transition kind;
- target creation time.

On successful prompt completion, persistence must atomically:

1. Finish the prompt operation.
2. Activate the pending transition.
3. Move the previous provider into history.
4. Make the target authoritative.
5. Persist the response/checkpoint.

The JSONL/v2 runtime currently prohibits activation during an active operation, so it needs a dedicated combined terminal operation such as:

```ts
finishOperationWithTransitionActivation(...)
```

This is preferable to two writes that could leave the completed response and active provider mapping disagreeing after a crash.

## 6. Mode changes

Mode changes need explicit treatment:

- Degraded → ACP creates a runtime-only provider attachment.
- ACP → degraded produces no loadable provider ID and should deactivate the previous mapping only after the mode transition succeeds.
- ACP → ACP with a fresh thread follows the regular pending/recorded lifecycle.

The SQLite provider-session repository likely needs an explicit operation:

```ts
deactivateActive(agentConversationId, deactivatedAt, transitionId?)
```

Appending another provider row currently deactivates the previous row, but switching to a mode with no provider ID cannot use that mechanism.

## 7. Direct JSONL/v2 creation

Initial direct-persistence checkpoints should no longer store a newly issued provider ID before a completed prompt.

Creation should write:

```text
checkpoint.internalSessionId = null
live attachment = runtime_only
```

After the first completed prompt, the transcript runtime atomically materializes the provider attachment into the checkpoint.

Opening a never-prompted direct conversation must recognize:

```text
no provider ID
no completed operation
```

and create a fresh provider thread without requiring continuation reconstruction.

## 8. Direct JSONL/v2 transitions

Apply the same transition semantics:

- `target_created` records runtime observation.
- `target_activated` remains the authoritative checkpoint change.
- Failed seed does not activate target.
- Promptless reset leaves an unactivated target record that the reducer safely ignores after restart.
- The first later successful prompt performs combined operation completion and transition activation.

Legacy JSONL v1 can use the same conceptual boundary, but its exact representation should be handled separately from v2 rather than weakening the v2 state machine.

## Stage 2 tests

Add coverage for:

- Same-adapter handoff keeps the source active until target seed succeeds.
- Cross-adapter switch does the same.
- Failed seed stops the target and restores/retains the source.
- Successful seed records and activates the target.
- Optional target-prompt failure does not invalidate an already successful seed.
- Promptless reset returns a runtime-only target.
- Restart after promptless reset loads the prior recorded mapping.

- Crash between target creation and prompt leaves the previous mapping authoritative.
- Degraded transitions correctly deactivate or delay provider mappings.
- Direct v2 creation has no provider ID before the first completed prompt.
- Direct v2 reopening of a never-prompted session starts fresh.
- Direct v2 first prompt records the provider attachment.
- Transcript reduction ignores unactivated created targets.
- Combined prompt completion and target activation recover consistently after truncation/failure injection.
