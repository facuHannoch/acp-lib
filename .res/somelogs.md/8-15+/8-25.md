I propose a compatibility-preserving, two-layer fix.

### 1. Model ACP response chunks

Add:

```ts
export interface ResponseChunk {
  text: string;
  messageId?: string;
  startsMessage: boolean;
}

export interface ResponseMessage {
  messageId?: string;
  text: string;
}
```

Extend `PromptResult`:

```ts
export interface PromptResult {
  /** Legacy flattened projection. */
  text: string;

  /** Assistant messages in protocol order. */
  messages: readonly ResponseMessage[];

  stopReason: string;
  status: "completed" | "cancelled" | "error";
  usage: Usage | null;
}
```

### 2. Preserve streaming compatibility

Keep the existing callback and add a structured one:

```ts
export interface PromptHandlers {
  /** Legacy text-only stream. */
  onChunk?: (text: string) => void;

  /** Boundary-aware ACP stream. */
  onResponseChunk?: (chunk: ResponseChunk) => void;

  // existing handlers...
}
```

Each ACP chunk invokes both callbacks. Existing consumers continue working; the hub migrates to `onResponseChunk`.

### 3. Replace `extractChunkText`

Introduce:

```ts
function extractResponseChunk(
  update: schema.SessionUpdate,
): { text: string; messageId?: string } | null
```

Keep `extractChunkText()` temporarily as a deprecated compatibility wrapper.

### 4. Accumulate messages correctly

Use one internal accumulator shared by `AcpClient` and, where necessary, `AgentSession`.

Rules:

- The first text chunk starts a message.
- A matching explicit `messageId` continues the current message.
- A different explicit `messageId` starts a new message.
- A missing ID does not create a boundary because no boundary can be inferred safely.
- If an ID first appears after unidentified chunks, adopt it for the current message.
- Never insert spaces or newlines into message text.

Example:

```ts
[
  { messageId: "m1", text: "I’m checking " },
  { messageId: "m1", text: "now." },
  { messageId: "m2", text: "Finished." },
]
```

becomes:

```ts
messages: [
  { messageId: "m1", text: "I’m checking now." },
  { messageId: "m2", text: "Finished." },
],
text: "I’m checking now.Finished."
```

The flat `text` remains intentionally unchanged for compatibility; consumers wanting correct presentation use `messages`.

### 5. Propagate through `AgentSession`

`AgentSession` should:

- Forward `onResponseChunk`.
- Preserve partial messages if a prompt fails or is cancelled.
- Return `messages` in lifecycle `turn_completed` results.
- Deep-copy/freeze the message collection in `copyPromptResult()`.

The degraded PTY client should produce one unidentified message because it cannot discover ACP boundaries.

### 6. Extend transcripts without breaking readers

Keep one transcript line per turn, adding an optional field:

```ts
interface TranscriptMessageLine {
  // existing fields...
  text: string;
  messages?: readonly ResponseMessage[];
}
```

New assistant entries persist both:

```json
{
  "v": 1,
  "t": "msg",
  "role": "assistant",
  "text": "I’m checking now.Finished.",
  "messages": [
    { "messageId": "m1", "text": "I’m checking now." },
    { "messageId": "m2", "text": "Finished." }
  ]
}
```

Old transcript readers continue using `text`. The hub uses `messages ?? [{ text }]`.

### 7. Hub migration

The hub should carry `messages` through runtime events and persistence. The webapp should render each entry as a separate assistant block or paragraph without modifying its text.

Existing flattened transcripts remain flattened; their original boundaries cannot be recovered.

### Tests

I would add coverage for:

- Multiple chunks with the same ID coalesce.
- A changed ID creates a new message.
- Missing IDs do not create guessed boundaries.
- Structured and legacy streaming callbacks both fire correctly.
- `PromptResult.text` remains backward-compatible.

This fixes the information loss at its source while providing a safe migration path for existing consumers.
