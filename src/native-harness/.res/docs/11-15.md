**We’re free to rewrite storage, contracts, or the loop.** My earlier statement described the benefit of separating responsibilities, not a restriction on changing them.

For now, I wouldn’t introduce a database: the in-memory store is enough to explore the context model. But its schema and operations are provisional. This is a good moment to revise them if the model calls for it.

Here’s the implementation as it stands.

**1. `start`: creates and runs the agent**

```sh
bun run start
```

`src/interfaces/cli/main.ts` dispatches to `start.ts`, which assembles:

- Configuration: system prompt, provider credentials, model, socket path.
- One `SharedContextStore`.
- One agent with per-channel execution queues.
- The model client and configured tools.
- The Unix-socket listener.
- The browser inspector.

`start.ts` owns the process-level assembly and shutdown.

**2. `chat`: connects a terminal client**

```sh
bun run chat channel1 alice
```

`chat.ts` reads terminal input and calls `sendLocal()`. Each request carries:

```ts
{ channelId, participantId, text }
```

HTTP over the Unix socket delivers it to `serveLocal()`, which calls `agent.send()`.

The client doesn’t own conversation state. It can disconnect and reconnect while the agent stays alive.

**3. `createAgent`: accepts and schedules inputs**

`kernel/agent.ts`:

- Assigns a turn ID.
- Appends the incoming message to the shared store immediately.
- Queues execution within its channel.
- Allows different channels to execute concurrently.

Channels currently own scheduling state—not independent context arrays.

**4. `SharedContextStore`: owns the recorded information**

`state/storage/shared-context.ts` holds an append-only array of entries:

```ts
{
  seq,
  at,
  channelId,
  turnId,
  from,
  message
}
```

It provides `append()`, `snapshot()`, and `subscribe()`. Entries and snapshots are deep-copied. There is no database or persistence yet.

**5. `runTurn`: coordinates inference and tools**

Before every model call, `kernel/loop.ts` invokes `context.build()`.

The composition supplies two operations:

```ts
context.build()          // snapshot store and construct model messages
context.append(message) // record a response or tool result
```

The loop continues through tool requests until the model returns no tool calls. Notices are not implemented yet.

**6. `buildContext`: constructs the inference view**

`capabilities/context/build.ts` currently produces:

```text
System prompt, unchanged

Current channel and participant
Shared history from all other turns, as attributed JSON

Active turn’s messages, in native conversation format
```

Tool definitions are supplied separately to the model client.

That presentation is intentionally basic. **There is one shared source of information, but a distinct rendered request for each active turn.** The builder currently moves other turns into a shared-history block rather than presenting one globally interleaved native conversation.

**7. Model, tools, and inspection**

- `openRouter()` translates neutral messages into the provider request.
- `executeCurrentTime()` implements the only configured tool.
- Inspection wrappers capture request bodies and execution status.
- The inspector derives channel histories from the store and streams updates through SSE.

So the overall flow is:

```text
chat → local HTTP → agent.send → shared store → channel queue
                                                   ↓
                         buildContext ← store snapshot
                              ↓
                         model → tools
                              ↓
                         shared store
```

**The main thing to evaluate next is the information model and its rendering—not which database to use.** Once those are right, we can decide whether the store needs different operations or a different implementation.





# instrucytion


## process killing


Find the process using the socket:

```sh
lsof -nP /tmp/native-harness-1000/agent.sock
```

Then stop it using the PID shown:

```sh
kill <PID>
```

If no process is using it, it may be a stale socket file. Remove it and restart:

```sh
rm /tmp/native-harness-1000/agent.sock
bun run start
```

Avoid removing the socket while its process is still running.
