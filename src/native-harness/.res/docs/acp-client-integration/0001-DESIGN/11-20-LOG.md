## Step 1 · Gate 1 contract: startup channel changes (2026-11-20)

Commit `83c2d0f`.

**Done.** Recorded
[decision 0020](../../../decisions/0020-startup-channel-changes.md) and added
the contract types to `src/contracts/protocol.ts`: `PendingChannelChange`,
`ChannelChangeResult`, optional `channelChanges` on `session/create` and
`session/load` params and results, and `capabilities.startupChannelChanges`.
Exported the batch and load-view types from the public `client.ts`. Types only,
landed before the implementation as AGENTS.md requires.

**Checked.** `bun run typecheck`.

**Gaps.** No behavior yet at this commit.

**Regressions.** None.

**Decisions and drift.** This closes the SPEC's open item "finalize the
pending-change result shape":

- Names are the ones PROTOCOL.md proposed. The request and result field is
  `channelChanges` on both create and load.
- A different batch on an already-open connection fails `invalid_state`.
  PROTOCOL.md says "rejected" without naming a code.
- An unknown policy name fails `invalid_policy`; other malformed batches fail
  `invalid_params`.
- **Atomicity drift.** PROTOCOL.md says to "resolve each channel change
  atomically with its channel state". The implementation composes the existing
  channel transitions (create, edit, suspend, resume, delete), so one entry is
  several storage transactions. Nothing can interleave: the session is not
  started and the endpoint admits no other request until the open is answered.
  A crash mid-entry leaves a prefix applied with no confirmation, and the host
  resends. This avoided a storage-contract change and a new conformance suite.
  A single-transaction storage operation remains possible later.
- To keep a blocked entry from half-applying, the lifecycle step is decided
  before the name and policy are written. A blocked entry writes neither.
- A retirement of a channel the harness has never seen creates it and retires
  it, so the ID is reserved like any other retired ID.

## Step 2 · Gate 1 implementation: batch applied at open (2026-11-20)

Commit `f564290`.

**Done.**

- `src/interfaces/protocol/channel-changes.ts` (new): whole-batch validation,
  policy check, batch comparison, and application in two phases. Suspensions,
  edits, creations and retirements run first. Resumes run last in a synchronous
  step shared with the load view, because resuming a checkpoint makes its turn
  run on the next microtask.
- `src/interfaces/protocol/server.ts`: `session/create` and `session/load`
  parse the batch before opening, apply it after recovery and before `start`,
  record the batch and its results on the endpoint, and return them. A repeated
  load with the same batch or none returns the recorded results.
- `README.md`: describes the behavior.

**Gate 1 evidence** (`test/startup-channel-changes.test.ts`, 8 tests, real
`serve --stdio` child processes on SQLite unless noted):

| Required evidence | Test |
| --- | --- |
| Offline suspension prevents early execution | Session killed with `a2` accepted and untaken. Reopen with `a: suspended`: view shows `a` suspended with `a2` pending, channel `b` runs a turn, `a` starts nothing, and a live resume takes `a2` once. |
| Invalid batches leave channel state untouched | Seven invalid batches (duplicate channel, unknown policy, missing `changeId`, bad lifecycle, unknown field, empty name, non-array), each with a valid first entry. All rejected, no events, and a following plain load shows `a` open and unnamed and no new channel. |
| Blocked delete suspends the target and preserves accepted work while another channel remains usable | Reopen with `a: retired`: `blocked`/`channel_busy`, `a` suspended with `a2` still `received`, the name in the blocked entry not written, `b` renamed and runs. After withdrawing `a2`, the same batch applies. |
| Lost open response is safe to retry on the same connection | Second load with the same batch and with no batch returns equal results and an equal status (same revision). A different batch fails `invalid_state`. |
| ...and after reconnect | Fault injection kills the process right after the suspension commits, before the response. A new process given the same batch reports `applied`; one turn, two items, nothing started on `a`. |

Also covered: a repeated retirement is `applied`; reopening a retired ID is
`blocked`/`channel_retired`; retiring an unknown ID reserves it; a batch resume
continues a checkpoint with all of its work events after the open response; an
incompatible checkpoint is `blocked`/`incompatible` and stays suspended;
`session/create` applies a batch on an in-memory server.

**Checked.** `bun run typecheck` clean. `bun run test`: 298 pass, 0 fail
(42 files) — the 290 baseline plus the 8 new tests.

**Gaps.**

- Crash points inside a batch are exercised at one boundary only (after
  `beginChannelSuspend`). A crash between a blocked retirement's check and its
  suspension, or between a create and its edit, is argued idempotent but not
  tested.
- A storage failure in the middle of a batch fails the open and leaves a prefix
  applied. Not tested.
- `session/create` with a batch whose policy is only known from a saved or
  sidecar configuration is validated after the session is created. A rejection
  then leaves the created session on disk without its config committed. With
  an inline config (what acp-client sends) the check runs before creation.
- A load view too large for one frame fails after the batch was applied.
- Session-level suspension combined with a batch is covered only by reasoning
  (channel controls are allowed in every session lifecycle).
- Events emitted while the batch applies (`channel_state`) are published before
  the open response, with revisions at or below the view's. That matches the
  load contract but a host must tolerate them; the adapter tests in Gate 2
  cover the host side.

**Regressions.** None found. Two behavior changes to existing paths, both
reviewed: the endpoint's "one open at a time" guard now stays set from the
storage open until the session is published, closing a small window in which a
second open could start; and an open that fails after a batch was applied stops
the session before releasing it.

**Drift.** As listed in step 1. `server.ts` is now 400 lines, at the AGENTS.md
review threshold; the batch logic was placed in its own module for that reason.

## Step 4 · Gate 2: the acp-client adapter (2026-11-20)

Commit `58860fd`.

**Done.**

- `src/native/records.ts`: what the host remembers across a harness restart.
  Each channel's newest unconfirmed desired state, with a version that is the
  wire `changeId`, and each input with its exact payload and a state (`saved`,
  `unknown`, `accepted`). In memory by default; `createFileHostRecords` keeps
  the same data in one JSON file.
- `src/native/host.ts`, `NativeHarnessHost`: one per Agent. Lazy single start
  through the host launcher (new launch kind `native-harness`), the open
  sequence (handlers, `initialize`, capability check, `session/load` or
  `session/create` on `not_found`, with the pending batch), reconciliation,
  per-channel ordering of live edits and inputs, reopen after a loss, and
  process shutdown.
- `src/native/controller.ts`, `NativeController`: implements
  `ConversationController` for one channel. Holds each reported turn's events
  and outcome until the prepared turn's `prompt()` attaches. `forceStop()` is a
  targeted `channel/interrupt` plus local settlement. `startFresh()` throws
  `UnsupportedError`.
- Wiring, all opt-in: `NativeAdapter` (`{ kind: "native" }`),
  `AgentConfig.harness`, `agent.nativeHarness`, a `native` binding on the
  session config, and the branch in `conversation-controller/factory.ts`.
  Creating a conversation with a title records the channel name; deleting one
  records its retirement. Neither starts the process.
- `conversationCapabilities.freshContext?: false` and the guard
  `requireFreshContext`, used by `restartProviderFresh` before it tears
  anything down.

**Checked.** Root: `bun run typecheck` clean; `bun test ./test` 1389 pass,
0 fail (129 files; 1335 baseline + 54 native at this commit). Harness: typecheck
clean, 298 pass, 0 fail. `bun test ./test/native` ran three times in a row
without a failure.

**Gaps.**

- **Host records are not in acp-client's persistence.** The spec says to use
  the host's prompt record. The records are behind an interface with a memory
  and a file implementation; the Agent uses memory unless given another. They
  survive a harness restart, which is what the checkpoint needs, but not an
  acp-client restart unless the file store is configured. The original
  design's `channels?` repository is not built.
- **Reconciliation after an acp-client restart is partial.** A fresh controller
  only settles turns it was following and turns that own one of its unsettled
  inputs. Turns that ended while no acp-client process existed are not
  recorded: that needs the durable watermark of the original design.
- **Events for a channel with no open conversation** are held in memory (2000
  per channel, oldest dropped) until one attaches. The conversation is not
  loaded from persistence to record them.
- **Not forwarded yet:** usage (metering records say "harness reported no
  usage"), `items_receipt` beyond a per-controller lookup (`receiptOf`), and
  `channel/withdraw` (the host has `withdraw`, but the session's local withdraw
  does not call it; this is the reviewed base's documented behaviour).
- **Stall detection is not paused** while the host reopens.
- **A request to the running harness times out after 30 s** (configurable).
  `channel/suspend` waits for a running tool, so a long tool can time it out;
  the change then stays pending and goes with the next open.
- `text: "stream"` is implemented in the controller and unit-tested, but the
  real-process tests use `final`.
- Restart limits (3 within 60 s) are tested with the in-process harness only.

**Regressions.** None found in the two suites. Behaviour changes to existing
code, all additive:

- `LaunchKind` gained `"native-harness"`. A consumer launcher that switches
  exhaustively on the kind will see a new value, only when a harness is
  configured.
- `AgentAdapterRegistration.adapter` and `AgentConfig.adapters` now accept a
  native adapter. `AgentAdapterRegistry.require/get/list` still return the
  `Adapter` shape; a native adapter appears there with the placeholder command
  `["native-harness"]`. Code that spawns that command for a native adapter id
  (internal inference on the harness runtime, adoption, a handoff target)
  would fail to spawn. None of those paths is supported for native yet.
- `agent.conversations.delete` reads the active provider session when a
  harness is configured, to learn whether the conversation is native. One
  extra read, only for Agents with `harness`.

**Decisions and drift.**

- **Open decisions from the spec, as implemented.** Launcher contract: the
  existing `AcpLauncher.prepare`, with kind `native-harness`; without a
  launcher the process inherits the environment plus `harness.env`. Startup
  deadline: 30 s from spawn to the open response, configurable; on expiry the
  process is killed. Retry of a failed launch: none automatic. A failed start
  rejects the operation that needed it and the next use tries again. Only an
  unexpected loss with work outstanding (a waiting input, or a conversation
  with a turn) is reopened by the host, at most 3 times in 60 s; then the host
  is `failed` until `restart()`.
- **Change to the reviewed session base (flagged for review).**
  `conversation-turns/backend-turns.ts`, `context.ts` and `run-turn.ts`: a
  turn the backend started now runs with the handlers of the first message it
  took that brought any. Before, such a turn had no consumer handlers, so a
  permission request could only be answered by `defaultPermission`, and the
  spec's "route the approval through the consumer" was not reachable from the
  public conversation interface. A turn that took no message, or whose
  messages brought no handlers, behaves as before. The 238 controller and
  turn-path tests pass unchanged.
- **Change to the shared conformance suite.** `Subject.backendScheduled`
  relaxes three assertions for the native subject, each following from the
  reviewed base's rules for backend-started turns: no `<turn>:user` record,
  no `endedBy`, and no `turn_failed` for a message the backend never accepted
  (no turn existed). The other subjects are unaffected.
- **Known consequences of the base for native conversations**, not changed
  here: a prompt's text is not written as a user record, and `endedBy` is not
  reported.
- **`abandonTurn` does not interrupt.** The original native design said it
  interrupts a running turn; the controller contract says it never stops
  provider work. The contract was followed.
- **`stop()` of a conversation interrupts its own turn** (original design).
- **A prompt to a suspended channel is refused** (`channel_suspended`) rather
  than held by the host.
- **A prompt whose start failed is never executed later.** A submission is
  `saved` until a push for it is written; a `saved` one is dropped when its
  caller is told the start failed. The spec's "retry unresolved submissions"
  applies to `unknown` ones.
- **A blocked change is not resent while running.** It stays pending and is
  re-evaluated by the next open, or sooner if the consumer changes it.
- **`freshContext` is optional and only ever `false`.** Making it required
  would have broken existing exact-equality assertions on the capability
  object.
- Turn ids reported to the session are `native-turn-<harness turn id>`.

**Gaps.**

- Step 5 loses the harness process. A lost connection with a live process (a
  broken pipe) is exercised only with the in-process harness.
- Step 6b's retry is the consumer's next prompt, because a failed start is not

Gro approved behavior revision `7133c5c651122d1736f25ca358c6f34b49a9ff10`
on a clean tree, covering Gates 1–3. The accepted chain includes startup contract
`83c2d0f`, harness implementation `f564290`, controller integration base

Both independent typechecks passed. Root `bun test ./test` passed 1391 tests
with 5868 assertions across 129 files (197.78s), including the nine native
conformance cases and the late-connection regression. The real SQLite stdio
checkpoint verified shared startup, steering and approval, isolated force stop,
missed-reply reconciliation, lost push and open responses, and Agent reopen and
shutdown. The harness suite passed 297 tests and had one stdio timeout on
`session/create` in the incompatible-checkpoint case (42 files, 149.11s).
Its in-process twin passed, and the isolated suspension suite passed all 15
tests with 196 assertions (7.42s). The reviewer accepted the rerun and retained
the existing client timeout. Local exploratory suites overlapped with each other
and with edits, so the clean-revision independent runs are the acceptance evidence.

The review reproduced a launcher timing gap beyond the existing initialize
timeout coverage. The regression isolated the late connection, and the fix
fenced subsequent startup work as well. A late connection still increments
the launch count before being closed.

Accepted limitations include composed startup channel transitions under decision
0020. A crash can leave a prefix applied, and the host resends the newest
unconfirmed desired state. Repeated loads on the same connection return the
recorded results. Default host records are in memory. Host process restart
requires a supplied file store to retain those records, and restoring in-flight
host work across host process death is outside this checkpoint. Failed-start
saved submissions are dropped. Unknown submissions are retried after reopen,
and an ambiguous push is repeated once. Unavailable or stale approval answers
return false without retry.

Usage is not forwarded, session-local withdrawal does not reach host withdrawal,
and receipt updates are available only through receiptOf. Backend-scheduled
conformance allows no user record, no endedBy, and no turn_failed if the backend
never accepted the message. The handler wiring for backend-started turns was
accepted. The real child checkpoint uses final text mode. Recovery pages messages,
with bounded turn and input recovery deferred.
