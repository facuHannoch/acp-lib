##### Shell




Most coding harnesses expose **one general command tool plus a few specialized file tools**. The model sees a tool called `shell`, `bash`, or `terminal` and passes it a command string. `git`, `sed`, `cat`, and `python` are programs it can name inside that string. The harness controls where the command runs and what output comes back.

| Harness | What the model can call |
|---|---|
| **OpenCode** | `shell` takes a command, working directory, and optional timeout. `read`, `grep`, and `glob` are separate tools with structured, bounded results. OpenCode documents that its shell runs with the host user’s authority. [OpenCode tools](https://opencode.ai/docs/tools/) |
| **Pi** | The default coding set is `read`, `bash`, `edit`, and `write`. Its local `bash` runner spawns a shell and captures output. Pi also offers a read-only set with `read`, `grep`, `find`, and `ls`. [Pi tool sets](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/src/core/tools/index.ts) · [Shell implementation](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/src/core/tools/bash.ts) |
| **Hermes** | `terminal` runs shell commands. Separate file tools cover reading, finding, and patching. It also exposes `execute_code` for Python scripts that can call Hermes tools and process their results. [Hermes tools](https://hermes-agent.nousresearch.com/docs/reference/tools-reference) · [Python execution](https://hermes-agent.nousresearch.com/docs/user-guide/features/code-execution) |
| **Claude Code** | `Bash` is the general command tool. It can run under an OS-level sandbox that constrains filesystem and network access for the shell and its children. [Claude Code sandboxing](https://code.claude.com/docs/en/sandboxing) |

### What `sed`, `cat`, and Python buy you

- **`sed`** processes text line by line. Agents often use `sed -n '40,80p' README.md` to print a small slice of a file, or `sed` substitutions to transform text. `sed -i` edits the file in place. The line-reading use fits a bounded `read` tool. The editing use belongs with whichever agent has write access. [GNU sed manual](https://www.gnu.org/software/sed/manual/sed.html)
- **`cat`** prints or concatenates files. A structured `read` can serve the common inspection case with line numbers and pagination.
- **Python** is useful when there’s actual computation or data processing, such as comparing two JSON reports. Running model-written Python grants general code execution within whatever environment it receives. That’s the same isolation decision as offering a shell.

### Where I’d draw the line for our harness

**Give the agent bounded workspace inspection now, and make general execution one optional capability.** In the first pass, I’d expose `read` for files and directory listings, `search_files` for filenames and contents, and `git_info` for the branch and current commit. “Which branch am I on?” should be one local call against the workspace attached to that conversation. The handler can invoke `git branch --show-current` directly with fixed arguments and report detached HEAD explicitly. [Git branch reference](https://git-scm.com/docs/git-branch)

There are three different execution designs worth distinguishing:

1. **Fixed operations.** The tool takes a workspace and typed arguments. The implementation decides how to perform the operation, including whether to spawn Git directly. This gives us a small, predictable surface for routine questions.
2. **A command runner that takes an executable and argument array.** This avoids shell interpretation. It’s useful when the permitted operations have fixed argument shapes. An executable allowlist alone is weak: allowing arbitrary Python arguments already lets the agent run code, and individual commands can have both read and write modes.
3. **A sandboxed shell.** This is the flexible option when the agent needs pipelines, scripts, or utilities we haven’t anticipated. The permission gate controls whether the channel may invoke the tool. The sandbox controls what the command can actually do. I’d give it an explicit workspace, a clean environment without provider credentials, restricted network access, and cancellation that applies to child processes too. Pass the working directory on each call so concurrent channels can operate independently.

I’d skip a catalog of individual Unix commands. If we keep getting requests that go beyond `read`, `search_files`, and `git_info`, that’s evidence for **one sandboxed command tool**. Simple workspace questions stay local, and coding changes, builds, and tests can continue through workers.



Yes. I’d give the agent **one `shell` tool** that can run commands in any directory available to its execution environment. The `git_info` proposal drew the line in the wrong place. The distinction we care about is whether the agent can do the work directly or whether a coding worker would do it better.

### How the shell tool works

The model sends a command and a working directory. For example:

```json
{
  "command": "git branch --show-current",
  "cwd": "/dir3/d"
}
```

The harness starts a shell in `/dir3/d`, captures stdout, stderr, and the exit code, and returns them as the tool result. The next call can use a completely different directory. Each call has its own working directory, so concurrent channels can work without changing one another’s state. A command can also contain `cd` to change directories within that invocation.

The execution environment determines which directories and programs are available. If it has Git, Python, and `glab` installed, the agent can use all three through the same tool. Checking a local branch works the same for a GitLab or GitHub repo. Querying GitLab for merge requests also requires network access and whatever credentials the deployment provides to `glab`.

### How that differs from option 2

| | What the model sends | What runs |
|---|---|---|
| **Direct execution** | `{ "program": "git", "args": ["branch", "--show-current"], "cwd": "/dir3/d" }` | The runner starts `git` directly and passes those arguments exactly. |
| **Shell execution** | `{ "command": "git diff --stat \| tail -n 10", "cwd": "/dir3/d" }` | The runner starts a shell, which interprets the pipeline and starts both programs. |

For a single command, either works. **The shell adds composition**: pipelines, redirects, variables, loops, and chaining commands. Direct execution can still run Python or any other installed program. The difference is who interprets the input, while **sandboxing is a separate choice** that applies equally to both.

A subprocess by itself runs with the access it receives from its launcher. A sandbox puts that subprocess and its children inside an environment with defined filesystem, network, and resource access. That could be an existing Agent container if it already provides the boundary we want. The harness can send commands to a runner there and keep its own model and search credentials in the process that uses them. We can configure the command environment with the directories and credentials it actually needs. [Pi shell implementation](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/src/core/tools/bash.ts) · [Claude Code sandboxing](https://code.claude.com/docs/en/sandboxing)

**For M2, I’d start with foreground `shell(command, cwd)`** through the existing tool lifecycle, with bounded output, cancellation, and an operator-configured deadline. That lets the agent check a branch, inspect files, run a Python snippet, or make a small change itself. The orchestrator remains valuable for work we want another agent to own independently, especially long-running tasks or changes that benefit from a coding specialist.
